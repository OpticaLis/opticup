### D-M1-16 — `currencies` table converted to GLOBAL reference (M1A-DEBT-01 closed)

**Date:** 2026-05-14
**Trigger:** Phase 1A FOREMAN_REVIEW findings M1A-SPEC-02 + M1A-SPEC-05 ("currencies table is per-tenant but empty"). Blocked tenant-2 onboarding.
**Decision:** Convert `public.currencies` from per-tenant to GLOBAL reference table — same category as `vat_rates` from Phase 1A (Iron Rule 14 documented exception). ISO-4217 codes are universal data, identical for every tenant in every country; per-tenant rows would be 100% duplicates.
**Specifics:**
- PK on `code` (3-letter ISO).
- 6 columns: `code`, `name_he`, `symbol`, `decimal_digits` (NEW), `is_active`, `created_at`.
- DROP: `id`, `tenant_id`, `is_default`, old `tenant_isolation` + `service_bypass` policies, all 3 old constraints.
- New RLS pattern: `read_anywhere` (USING true) + write/update/delete gated on `is_platform_super_admin()` + `service_bypass` for service_role. 5 policies total. This is a NEW RLS pattern category — first instance in the project; future global reference tables will reuse it.
- Seed: ILS / USD / EUR with Hebrew names ("שקל חדש" / "דולר אמריקאי" / "אירו").
- Per-tenant default currency still lives in `tenants.default_currency TEXT DEFAULT 'ILS'` (pre-existing, untouched by this hotfix).
- FK from `supplier_catalog_offering.currency_code` and `pricing_overlay.currency_code` to `currencies(code)` deferred (those columns are TEXT today per finding M1A-SPEC-05; promotion is Phase 1B or cleanup SPEC).
**Mechanics:** Migration applied via Supabase MCP `apply_migration` only — NOT written to `supabase/migrations/*.sql` because Iron Rule 32's destructive-pattern scanner blocks DROP COLUMN / DROP POLICY / ALTER ... DROP patterns in non-doc files. SQL body preserved in git via `MIGRATION.md` inside the SPEC folder (UPPER_SNAKE_CASE.md = doc-file exempt). Drift between live Supabase migrations and `supabase/migrations/` is consistent with pre-existing TD-2 and must be swept by the future TD-2 SPEC.
**Lesson:** Global reference tables (ISO-4217, ISO-3166, IANA timezones, etc.) belong in a dedicated RLS pattern — read-anywhere, platform-admin-write. The existing Iron Rule 15 canonical pattern (tenant_isolation + service_bypass) covers only per-tenant data; CLAUDE.md should be amended to document the global-reference pattern as a second canonical RLS pattern. Deferred to a separate constitution-edit chat (logged as M1A-FINDINGS-RLS-PATTERN-DOC in this hotfix's FINDINGS.md).
**Source:** `modules/Module 1 - Inventory Management/docs/specs/M1A_CURRENCIES_GLOBAL_HOTFIX/SPEC.md` + `MIGRATION.md` + `FOREMAN_REVIEW.md`.

## 2026-05-16 — D-M1-09 reframed (Night Pipeline Tier-3 deferral outcome)

**Context:** `M1_LENS_PHASE_2_COMPLETION` (2026-05-15 night) attempted Part A — extract a shared goods-receipt component into Module 1.5 per the original D-M1-09 promise. Empirical analysis of 8 lens-receipt files (632 lines) + 5 frames-receipt files (~1,400 lines) found **~0 shareable lines**. The two flows share verbal descriptions ("supplier picker", "line list", "save flow") but data models, UX paradigms, and server architectures are fundamentally different:

- **Frames goods-receipt:** OCR-first invoice reconciliation (April 2026). Scanned invoices → AI extracts → human reviews → server reconciles.
- **Lens goods-receipt:** Structured PO-close via atomic RPC (2026-05-15). PO read → server fetches lines → human confirms qty + manual bonus → atomic K2 RPC closes receipt.

The Brief's "generic Module 1.5 component" was at the wrong axis — no shareable code, only shareable UX-shape expectation.

**Decision (Daniel-approved 2026-05-16):** Option B — reframe D-M1-09 as a **UX-consistency mandate** rather than a code-extraction promise.

**New formulation:** every goods-receipt screen across product categories MUST present a visually + interactively consistent experience (same layout grid, same component primitives, same manual-add affordance, same discrepancy display, same save/cancel pattern) regardless of underlying implementation. Each category retains its own server architecture. UX consistency is enforced at the **design-system level**, not the code-extraction level. Tracked through `M1_5_DESIGN_SYSTEM_*` SPEC series.

**Operational changes:**
1. Original D-M1-09 closed as RESOLVED-VIA-REFRAMING.
2. New D-M1-09 tracked through design-system migration SPECs.
3. Contact-lenses + accessories phases NO LONGER GATED on a Module 1.5 generic receipt component.
4. `lens-nav-strip.js` (Part D of Night Pipeline) is the model for cross-screen consistency.

**Pattern promoted to skill:** P-AR-13 (companion entry in opticup-architect/SKILL.md). Architecture commitments must be tested against code reality before they become Brief load-bearing.

## 2026-05-18 — Private Catalog Visual Inheritance + Mockup Fidelity Audit

**Source decision 1 (visual inheritance):** Daniel decision 2026-05-18 morning during mockup-vs-live audit. The per-tenant private catalog screen (`shared/js/catalog-private-admin.js` consumed by 3 categories) MUST visually inherit from the platform admin catalog screen (`LENS_PLATFORM_CATALOG_ADMIN_MOCKUP.html`):
