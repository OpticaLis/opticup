## D-M1-01 — Stock vs Custom production type

**Daniel's correction:** flag belongs on `supplier_catalog_offering` (commercial offer), NOT on `lens_variant` (physical SKU). A custom lens CAN sit as `qty_on_hand > 0` at the optic — two independent attributes.

**Decision:**
- Field `production_type ENUM('stock','custom')` on `supplier_catalog_offering`
- Internal flag, hidden from end-user
- Same series existing in both forms → two separate `lens_design` rows (no visible suffix)
- Stock/custom is the **primary filter** in every M1 screen + future M7/M9

## D-M1-04 — Mockup 3 (Pricing): inline edit + bulk + no separate edit screen

- 3 columns: catalog / discount% / final price

- `pricing_overlay` gains a default layer at `lens_design` or `supplier` level
- Variant-level rows act as exceptions
- Resolver: variant first, fall back to default
- "Add 5% to all HOYA" = 1 row update, not 800

- CRUD on lens_brand / lens_design / lens_variant / supplier_catalog_offering
- For Optic Up platform admin only (us), hidden from optic
- Phase 2+: suppliers get direct write access; optic approves catalog changes

## D-M1-07 — Mockup 4 (Purchase Order): manual-send + source-split + customer link

- "📨 Send to supplier" → "📨 Mark as sent to supplier" (Phase 1 has no auto-send)
- PDF + Excel export = primary actions
- Lines split by source: stock-shortage (auto), custom-per-customer (auto from M7 — shows customer_id), manual additions
- Tenant setting: "auto-send custom orders to supplier" — default OFF
- Phase 2+: optional auto-send via email/WhatsApp/API

## D-M1-08 — New Phase 1 screen: Active Purchase Orders List

Master list across all suppliers, statuses: Draft → Sent to supplier → Partially received → Fully received.

## D-M1-09 — New Phase 1 screen: Goods Receipt

- **Anchor on existing frames receiving pattern** (`modules/Module 1 - Inventory Management/docs/goods-receipts/`)
- Mandatory: delivery-note / invoice number per receipt
- Optional: upload scanned PDF / phone-scan
- Lists open PO lines for the selected supplier; user marks what arrived (full/partial)
- Manual additions allowed (arrived not on PO) — flagged + audit-trailed
- Creates stock_lot with FIFO + receipt-date + unit_cost
- **Generic component in Module 1.5** — reused by frames/lenses/contact-lenses/accessories

## D-M1-10 — Reconciliation Agent: schema readiness (CRITICAL)

Future agent must verify nothing disappears between PO → delivery note → goods receipt → M7 sale. Schema must capture all event-time data NOW.

**Mandatory Phase 1 schema fields:**
1. `purchase_receipt.delivery_note_number`
2. `stock_lot.purchase_order_id`
3. `purchase_order_line.sale_order_id` (nullable, for custom-per-customer)
4. `purchase_discrepancy` table OR receipt-line discrepancy fields (`discrepancy_qty` + `discrepancy_reason`)
5. Timestamps: `ordered_at`, `sent_to_supplier_at`, `expected_delivery_at`, `delivery_note_received_at`, `goods_received_at`
6. `stock_transfer.actual_received_qty` (inter-branch coverage)

## D-M1-11 — Debt-record creation timing (correction)

**My initial recommendation:** auto-create supplier_debt at PO creation.
**Daniel's correction:** Debt is created from delivery note / invoice **at goods-receipt time**, never at order time. Orders can fall through.

**Lesson:** Accounting events follow physical events, not intent events.

## 2026-05-14 — M1 ↔ M9 Overlap Investigation (Architect mandate)

**Investigation commit:** 2199191 — `M1_M9_OVERLAP_REPORT.md` (581 lines)
**Verdict:** 🟢 PROCEED-WITH-M1-AS-IS. Zero genuine overlaps, 5 clean hand-offs, zero escalations.

### Findings summary

- **M1 = commercial/accounting record of inventory** (catalog, FIFO, PO, debt, transfers)
- **M9 = operational service flow** (lab_jobs, shipping_boxes, compensation)
- Three contract points: supplier identity (M1 read by M9), stock-inbound box hand-off (M9→M1), goods-received event (M1→M9)

### D-M1-15 — Legacy `shipments` module deprecation

Legacy `modules/shipments/*` + `shipments` / `shipment_items` tables are deprecated and absorbed by M9 (M9 Brief D3). M1 Lens Phase 1 introduces a separate `purchase_receipt` path that doesn't touch them. Cleanup is M9 SPEC scope.

## Schema deltas (all additive, no breaking changes)

```
supplier_catalog_offering
  + production_type ENUM('stock','custom') NOT NULL

pricing_overlay
  + scope_design_id UUID NULL  -- default layer
  + scope_supplier_id UUID NULL  -- default layer
  -- variant_id stays as exception layer
  -- CHECK exactly one of (variant_id, design_id, supplier_id) NOT NULL

purchase_receipt
  + delivery_note_number TEXT NOT NULL
  + delivery_note_received_at TIMESTAMPTZ
  + goods_received_at TIMESTAMPTZ
  + scanned_doc_url TEXT NULL  -- optional PDF/photo

stock_lot
  + purchase_order_id UUID  -- link to PO that spawned the lot

purchase_order (new or existing — confirm)
  + ordered_at TIMESTAMPTZ
  + sent_to_supplier_at TIMESTAMPTZ
  + expected_delivery_at TIMESTAMPTZ

purchase_order_line (new or existing — confirm)
  + sale_order_id UUID NULL  -- for custom-per-customer orders

purchase_discrepancy (new) OR add to purchase_receipt_line
  + discrepancy_qty INT
  + discrepancy_reason TEXT
  + discrepancy_status ENUM('open','resolved','accepted')

stock_transfer
  + actual_received_qty INT  -- inter-branch reconciliation
```
