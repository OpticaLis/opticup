## 2026-05-07 — M7 print forms protocol + first form (Outside Framing)


**Situation:** Daniel introduced the first M7 print form ("Outside Framing" = sent to external lens company for outside framing). Asked how to organize forms in general going forward.
**My recommendations + Daniel's responses:**

1. **Forms catalog file.** Created `M7_ORDERS_PRINT_FORMS.md` to register every form with: granularity (order/sub-order/item), use case, button location, barcode encoding. Daniel: implicit-agreed (asked me to document each form when closed).
2. **Granularity-tier discipline.** Every print button lives in the UI area matching its granularity. Per-sub-order forms = inside that sub-order's editor. Per-order forms = bottom toolbar. Mixing tiers in one button = design bug. Daniel: agreed.
3. **Print actions area separate from messaging area.** I recommended a dedicated "הדפסות לתת-הזמנה" block separate from the messaging block, because messaging goes to customer and printing goes to lab/cashier. Daniel: agreed.
4. **All barcodes on one form encode the same ID.** Multiple barcodes on a form (4 in this case) are positional redundancy for fold-/cut-tolerance, NOT different IDs. Locked.
5. **6 checkboxes are tenant-configurable.** Stock+Framing / Custom+Framing / Framing only / Lenses attached / Lenses already ordered / Custom lenses without framing — start as default seed per Iron Rule 19, tenant can edit.
6. **Future: AI auto-fill from lens-company forms.** The current generic form is the day-1 default. In the future each lens company uploads their proprietary form, AI fills it from sub-order data, employee just prints. Documented in the catalog file as the long-term direction.

**Lesson 1:** Every artifact-producing action (print, email, export) inherits granularity from the data it represents. Adding a granularity column to every catalog upfront prevents future tier-mixing bugs.
**Lesson 2:** Daniel uses "McDonalds App" as the internal nickname for the Lab module (M9). Track this — it's how he refers to it in conversation. Lab module is the receiver of Outside Framing barcodes.
**Lesson 3:** Forms catalog is the right pattern. Future modules with print outputs (M8 receipts, M11 reports, M13 loyalty cards) should each have their own forms catalog file using the same template.



## 2026-05-09 — M8 (Payments) Architecture Brief closed


**Situation:** Long M8 design session (per Pattern P23 — research-first). Four subagent dispatches: (1) 8-category market research, (2) focused API-requirements scan across Linet/Z Credit/CardCom/Tranzila/Pelecard/Gama/יחיד/Heshev, (3) reverse-sync capability scan, (4) legal POS requirements scan. All 4 dossiers archived in M8 folder.

**Critical correction mid-session #1:** I assumed Prizma is עוסק-פטור (incorrect). Daniel corrected — Israeli optical chains are עוסק-מורשה. Then Daniel re-framed the entire M8 direction: "M8 = ERP that orchestrates external POS, not a POS itself" — tax-invoice issuance stays in Linet/Z Credit/CardCom (certified קופה-רושמת), Optic Up just records receipt-numbers. Eliminated all our concerns about רשות-המיסים compliance.

**Critical correction mid-session #2:** I designed Checkout to record cash/checks only in Optic Up (no POS dispatch). Daniel corrected — Israeli law requires EVERY payment to pass through certified POS, including cash, checks, transfers. Only deferred check (צ'ק-דחוי) is the legal exception, and even that must go to POS on its clearing date. Full re-design of Checkout.

**Daniel's design decisions (locked):**
1. **6 active payment methods at Prizma** (credit/cash/transfer/check/bit/salary-deduction). "closed" and "deduction" reclassified as adjustments.
2. **Settlement mode (פדיון/תשלומים-רגילים) = tenant-level config**, NOT cashier choice. Daniel was sharp on this.
3. **Split entered in Optic Up FIRST.** No reverse-sync from Israeli POS is reliable. Cashier types split, then types each leg into Linet manually.
4. **Manual receipt-number entry day-1.** Future Linet webhook may eliminate this.
5. **Deferred check = the only legal exception.** Recorded in Optic Up day-of-sale, NOT through POS. On clearing day, banner-alert in main screen → click → dispatch to POS.
6. **N checks per order** with separate rows, separate clearing dates, separate alerts.
7. **"Invoice recipient name" field** — optional in every payment type, saved in customer history.
8. **Salary deduction = active payment method, NOT a separate screen.** Status "ממתין-לחיוב-משכורת" → "נוכה" after monthly checkbox in M11 report.
9. **Channel of clearing (ערוץ-סליקה) hidden by default.** Tenant-default is silent. Cashier clicks "🔄 ערוץ-אחר" only when needed. Available in ALL payment forms.
10. **Daily-close = manual entry of POS amounts.** Linet doesn't expose API; cashier types 5 amounts per channel from printed report. Mismatch turns row red.
11. **Print format = Hebrew sheet with checkboxes**, cash-line highlighted, dual signatures.

**Architectural decisions (locked):**
12. **Provider Adapter Pattern with 3 layers.** Adapter (code) → Adapter Manifest (DB) → Tenant Config (UI). Adding new POS = adapter + manifest, zero UI/Checkout changes.
13. **Schema-driven UI forms.** Each adapter declares credentials_schema_jsonb, UI builds form dynamically.
14. **Capability flags = global pool.** Adding Apple Pay/Google Pay/Crypto = row in pool, no UI change.
15. **Settlement modes = global pool.** Each adapter declares supported modes.
16. **Roles dropdown = reads from M2 tenant roles.** Not a hardcoded enum.
17. **Finance Hub = future module, NOT in MASTER_LIVE_PLAN.** Daniel directed: "אני רוצה שהתוכנה תיצא לאוויר בלי המודול הזה". Registered in MASTER_ROADMAP as future module. Permissions reserved for accountant + business-owner.

**Files produced** (in `modules/Module 8 - Payments/architecture-brief/`):
- M8_PAYMENTS_BRIEF.md v1
- 4 mockups: Checkout v3, Checks-Pipeline v1, Daily-Close v2, Provider-Config v2
- 4 research dossiers (market digest, provider-interface scan, reverse-sync scan, legal scan)

**Folder structure cleaned:** Daniel asked to organize architecture-briefs/ — moved all files into per-module folders (M5/M6/M7/M8/M14/M15) + _archive for old versions.

**Lesson 1 (process):** Pattern P23 (research-first for external integrations) was the right call. Without the 4 subagent dispatches, M8 Brief would be wrong on multiple axes (tax status, Linet API, reverse-sync, legal requirements). Each subagent caught a critical assumption.

**Lesson 2 (correction handling):** Daniel's mid-session "M8 isn't a POS" pivot meant abandoning ~40% of designed work. Embrace mid-session pivots when the new framing is clearly better — don't sunk-cost. The pivot took 30 min but saved weeks of wrong-direction.

**Lesson 3 (tenant config discipline):** Every "list of options" in this Brief became a tenant-config table — payment_methods, payment_channels, payment_capabilities, settlement_modes, roles. Going forward: any "list of values" in a Brief should immediately be a table, never an enum, unless it's a state-machine-of-internal-states.

**Lesson 4 (don't over-design screens):** I proposed a dedicated "salary deduction" screen. Daniel pushed back — and the right answer was existing payment-method + flag + report-with-checkbox. Default to "no new screen" unless workflow really demands it.

**Lesson 5 (separate-module litmus):** Daniel asked twice if features should be in M8 or a separate module. Both times answer was separate (Finance Hub). Pattern: if two features have different primary users and different permission levels, they're different modules.
