## 2026-05-06 — M12 promoted from "messenger" to "rule engine" — recall control layer


**Situation:** While discussing M6 recall split (M6=when, M12=how), Daniel raised: "I want M12 to also let me toggle recalls on/off, override channels, and shift the time (e.g. +2 hours)."
**My recommendation:** Yes — easy technically (3 fields: is_enabled, channel_override, send_offset_minutes). But also a structural upgrade — M12 becomes a rule-engine sitting OVER the business-fact layer (M6).
**Daniel's response:** Agreed, including extending offset to be negative (send before, not just after).
**Reason for agreement:** Operational flexibility without deploy, SaaS litmus passes (per-tenant rules), A/B testing, disaster recovery (kill-switch).
**Lesson 1:** When user asks "is X easy?", answer in two beats: (1) yes/no on cost, (2) is it RIGHT — does it improve the architecture or distort it. Don't just say "yes it's easy" — judge it.
**Lesson 2:** The "M6=fact, M12=rule" split is a generalizable pattern. M6 produces business facts (prescription expires at T). M12 decides whether/how/when to act on facts. Generalizes: M7 produces order-state-changes (fact); M12 decides whether to notify. M8 produces payment-events (fact); M12 decides confirmation messages. The fact-vs-rule separation is now a cross-module pattern — must propagate to M7/M8 briefs.
**Lesson 3:** Recall rules are per-tenant config, not per-tenant code. Belongs in M2 (Platform Admin) UI surface, with rules table per tenant. Adds dependency: M12 brief must declare a `recall_rules` (or `notification_rules`) table.


## 2026-05-07 — M7 messaging flow + sub-order ID format


**Situation:** Closing M7 messaging flow: when do messages send, who triggers them, what status updates ride on each send. Also the canonical sub-order ID format.
**My recommendations + Daniel's responses:**

1. **Sub-order letter is permanent for life.** Even after deletion, A/B/C never reassigns. Deleted letter shown dimmed in rail. Daniel: agreed.
2. **"Thank you" message is automatic on first payment (even partial).** Order without payment stays as Quote — inventory does NOT decrement, no "thank you" sent. Daniel: agreed and tightened — "I don't want a customer to receive 'thanks for buying' without actually finishing the order. Partial payment is enough trigger; zero payment = quote = no message, no stock decrement."
3. **"Sent for framing" customer-facing message:** I proposed adding it to reduce "when will it be ready?" calls. Daniel: declined for now. "Maybe in the future a customer-facing status window like Domino's pizza, but not now." Internal log entry only.
4. **Pickup-reminder message:** I proposed it as part of M7. Daniel: declined for M7 scope. "There will be such a message but don't plan it now. I want a Communications/Automations module where we build all those automations comfortably from one place."
5. **Manual now, automated later.** All status messages start as MANUAL buttons in M7. Bulk automations (timing rules, follow-ups, reminders) move to a future Communications/Automations module. Each manual button has an auto-twin path for the future.
6. **Status updates on the order ride on the message-send event.** "Order Ready" date logs ONLY if the WhatsApp send succeeded. If send fails — date doesn't move. Same model for "Sent for framing" (manual or scanned at lab module).
7. **Main-order status auto-aggregates from sub-orders.** Main "ready" flips only when ALL sub-orders are ready. Same for "picked up". UI: rail bottom shows counters "ready 2/4 · picked-up 2/4".

**Lesson 1:** Daniel draws a clear line between *order workflow* (M7) and *messaging automations* (future Comms module). Keep M7 messaging as pure manual-with-future-auto-hooks; do NOT pull automation rules into M7. The Comms module will own the if-then engine.
**Lesson 2:** "Don't send automated 'thanks' before customer has actually committed (paid)" — important UX/trust principle, not just a technical detail. The same logic likely applies to other automated outreach across the project: trigger only on customer commitment events, not on staff-action events. Worth checking other modules for similar exposure.
**Lesson 3:** Sub-order letter immutability is a foundational decision — every future code path that references "1-9362-A" depends on it. The letter is identity, not position.



## 2026-05-07 — M7 Form #3: Frame Reservation


**Situation:** Daniel introduced the third M7 form — "Frame Reservation" for clients/leads who want to hold a frame for a few days before paying.
**My recommendations + Daniel's responses:**

1. **Sub-order in `reserved` state, not a 5th type.** I recommended treating reservation as a state on a "frame" sub-order, not a new sub-order type. Daniel agreed.
2. **What can be reserved:** Frame ✓ · Frame+lenses ✓ · Contact lenses ✓ · Lenses-only ✗ · Accessories ✗. Daniel clarified: "Lenses can be reserved together with a frame (for convenience when converting to order). Standalone lenses don't need reservation. Accessories — no need."
3. **Inventory deducts immediately on reservation.** Daniel was firm: "When you put it in a bag with the form on the side — it's already out of stock. The reservation is the act of physically removing it." No "soft reserve" / "hold without deducting".
4. **Lenses inside reservation = "reserved choice", supplier order NOT yet placed.** Lenses are tracked but no PO is created until reservation converts to active order.
5. **Lead → customer auto-conversion on payment.** When a lead pays for their reservation, the lead is auto-promoted to customer. The reservation form shows "⚠ Lead" flag if applicable.
6. **System requirements (M7 scope, not on the form):** `reservation_expires_at` field, "Active reservations" screen with filters, "Convert to Order" button, history retention after conversion.
7. **Pop-up + WhatsApp on expiry: deferred to future Communications/Automations module.** M7 only stores the field + hook. Daniel confirmed.
8. **Print button visibility = state-dependent.** Frame Reservation print button is enabled only when sub-order is in `reserved` state. Other states: button is dimmed/disabled.

**Lesson 1:** State-dependent UI elements (a button that only fires for one state) are normal and good. Don't try to make every button always-clickable — let the state machine drive button visibility/enablement. Document the state→button matrix in the forms catalog.
**Lesson 2:** Daniel uses "physical reality" reasoning consistently — "if it's in a bag, it's out of stock". When in doubt about timing (when does X happen), ask: what's the physical action that triggers it? The system mirrors the physical workflow.
**Lesson 3:** Lead/customer is a soft boundary — the same person can be a lead today and a customer tomorrow without re-entering data. M5 architecture (single `customers` table with `lifecycle_stage`) supports this directly. The reservation form respects this by showing the lead flag when relevant, and the system auto-flips on first payment. Pattern P21 (overlap stories → one entity with stage) holds up here.

## 2026-05-07 — M5 Customer Card screen (5 tabs design)


**Situation:** Daniel showed 4 OpticPlus Access screenshots of the customer card (Details / Vision Function / Glasses / Contact lenses + the Docs screen). Asked for UX + architecture feedback.
**My recommendations + Daniel's responses:**

1. **Reduce 6 tabs to 5.** Merge Glasses + Contacts into "Eye Care" with a top selector. Replace "Update" tab (it's an edit-mode, not content) with "Docs" (medical documents upload — Daniel said this is what he wants). Daniel: agreed.
2. **Eye Care merged tab — top buttons not sub-tabs.** Two big buttons (משקפיים / עדשות-מגע) replace the entire content below. DB stays separate per M6 (prescriptions_glasses / prescriptions_contacts as two tables with different fields), but UI presentation unified. Daniel: agreed.
3. **Edit mode = button-in-header, not a tab.** Click "ערוך" in the customer header to enter edit mode globally — all tabs remain accessible, fields become editable. Daniel: agreed (implicit by approving the 5-tab plan with Update removed).
4. **Auto-save everywhere.** Same pattern as M7. No "Save" button. Daniel: agreed.
5. **Medical notes (Medical Q. + Diagnostics)** consolidated to one block with sub-tabs inside Details, not as separate full-screen popups. Daniel: implicit-agreed.
6. **Birthday auto-message deferred.** Was in OpticPlus card. I marked it as "future — Communications/Automations module. Manual for now." Consistent with Lesson from M7 that automation rules belong in a separate module.
7. **Orders tab = full M7 screen.** Click on Orders tab → screen layout switches to the full M7 mockup we already designed. Customer Card mockup shows just a summary + "open M7 screen" button. Daniel: implicit-agreed.
8. **Docs categories** added to handle long-term volume. Daniel: agreed (asked the question, accepted the recommendation).

**Lesson 1:** Tabs that look identical but represent different domains (Glasses vs Contacts) are a UX smell — even if the underlying data models are different, the user experiences them as "the same thing twice". Merging at the UI level while keeping data separate is the right pattern. Future modules with similar pairs (e.g., walk-in customer vs subscription customer): same approach — one screen, top selector.
**Lesson 2:** "Update" as a tab is an Access-era artifact (edit-mode-as-screen). Modern web/desktop apps use mode-toggle, not screen-switch. When migrating from Access UIs, watch for this anti-pattern.
**Lesson 3:** Customer card is the integration hub of M5/M6/M7/Docs. The same person can be touched from any direction — and the card needs to expose all sides without becoming a 12-tab monster. The pattern that works: 5 max top-level tabs, with sub-selectors inside (Eye Care 2-button, Medical sub-tabs, Vision Function date-selector). This is the "One screen, several lenses" pattern.



## 2026-05-07 — M5 customers-list: row-click + row-actions + sort/view + density + composite client number


**Situation:** Closed 4 sub-decisions on the customer list before locking the Brief.

### Decision 1: Row click opens customer card in NEW TAB
Three options considered: full-page replacement, new tab, side drawer. Chose **new tab**. Reason: optical staff handles customers in parallel (one on phone while another at counter); tabs let staff switch without losing place. Full-page forces back-and-forth. Side drawer too narrow for a 5-tab customer card.

### Decision 2: Row-end micro-actions = 3 buttons, configurable per-tenant
**Defaults:** 💬 WhatsApp · 📅 Schedule appointment · ➕ New order. **Pool of choices:** WhatsApp / SMS / "Show phone" (popover, no auto-dial) / Schedule / New-order / Task / Repair / Note. Tenant admin picks 3-4 from the pool.

**Daniel's clarification on phone:** "📞 Phone" button shows the number in a popover/tooltip (no auto-dial), copy-to-clipboard. With this in place — **the dedicated Phone column is removed**, freeing space for one more activity-content column. Net effect: even more activity, less identity. This actually *strengthens* Approach B beyond what we planned.

**Identity-anchor revised:** Only **name** is now the fixed anchor, not "name + phone". Phone is reachable via the row-action button.

### Decision 3: Sort + view-range = both selectable in table header
**Sort options (4):** Alphabetical / Last activity (default) / Last exam / Last order.
**View range (4):** Today / Week (default) / Month / All.

**Search bypasses the view filter.** When user types in quick-search, search runs across all customers in DB regardless of current view selection.

**Auto-complete dropdown.** Type any character → dropdown shows matching customers, narrows with each additional character. Works for name, phone, ID number, order number. Click on dropdown item → opens customer card in new tab.

**Strategic insight:** "View" and "Search" are now clearly separated — VIEW = "what do I want to look at right now" (today/week/month). SEARCH = "find a specific customer I have in mind". Two distinct UX intents, two distinct behaviors.

### Decision 4: Row density = configurable per-tenant (compact OR expanded with sub-line)
**Compact:** single line per row.
**Expanded:** main line + sub-line. Sub-line content also configurable per column. E.g., Daniel's preference: under name = phone+language, under last-exam = date+optometrist, under last-order = date+status.

This bundles together with column-set + column-order into one tenant-level setting: **"Customer-list display preferences"** in `tenant_settings`. Includes (1) which columns shown, (2) order, (3) density, (4) sub-line content per column when expanded.

### Decision 5: Composite Client Number = `[TENANT][BRANCH][CUSTOMER]`
**Daniel proposed:** Display the customer number as concatenation of tenant + branch + customer (e.g., tenant=4, branch=3, customer=545 → 43545). One number, used everywhere — card header, receipts, orders, reports, list.

**My initial pushback was wrong:** I worried it was confusing on customer-facing receipts. Daniel pushed back — the customer is created with this number, never changes, no actual confusion. I retracted.

**Final design locked:**
- Storage: `customer_number` (per-tenant, atomic via RPC per Iron Rule 11) + `home_branch_id` FK on customer.
- Display: composite `[TENANT_CODE][BRANCH_CODE][CUSTOMER_NUMBER]` formatted everywhere.
- **Fixed-width digits per part** (Module Strategist will specify exact widths in SPEC) so concatenation is always unambiguous and uniform-length.
- home_branch_id stays the same even if customer visits other branches — the displayed number doesn't change. "The number on the card" is the home-branch number, period.
- Branch closure: branch_code is **never reused** if branch ever held customers/orders. Branch with zero activity can be hard-deleted, freeing the code. Otherwise soft-delete only (Iron Rule 3 alignment for branches too).

**Migration note for Module Strategist:** Existing OpticPlus customer numbers (1-5028 for Prizma) carry over as `customer_number`. All Prizma customers will share Prizma's `home_branch_id` (single branch today). New tenant-2's first customer starts at customer_number=1 within that tenant.

**Daniel's responses across all 5 decisions:** Agreed.

**Lesson 1 (communication failure):** When I framed the Activity-first column choice, I confused Daniel — he asked "are you saying clicking a row should NOT open the card?". I had to clarify the click-behavior wasn't the question. **Future binary recommendations: include a one-line user-flow scenario** ("user opens screen, sees X. Clicks row, gets Y."), not just abstract column labels.

Going forward, propose configurability proactively rather than asking Daniel to flag it. Already known from earlier session lesson — now reconfirmed; promote to SKILL.md as a binding behavior.
