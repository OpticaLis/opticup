11. Brief sealed at 12 sections, 5 sketches, 13 decisions, 7 risks, 7 to-dos

**13 Locked Decisions:**

| # | Topic | Decision | Reason |
|---|---|---|---|
| D1 | Pricing model | Per-tenant choice (`flat_pricing` / `per_tier_pricing`). Prizma = flat. | SaaS-clean — different chains use different models. Both via config. |
| D2 | Renewal | Manual, not auto | Auto-renewal requires stored payment method (PCI scope) — out for LIVE day-1 |
| D3 | Tier downgrade | Yes, with 6-month grace, per-tenant | Without downgrade tiers lose value. With grace, no resentment shock |

| D6 | Family pooling policy | `equal` default + `head_only` available, per-tenant | Equal is simpler for customers; head-only fits Spotify/Apple Family pattern |
| D7 | Migration | None — start fresh | Existing `customers.qhaver=true` are leftover, no benefits owed |
| D8 | Coupons separation | M13 issues, M7 redeems | Pattern P9 (one entity, two homes) |
| D9 | Frames vs Lenses accrual | Model 1 — separate accrual rates, combined threshold | Customer thinks total spend, not category-split |
| D10 | Default category accrual | 0% — only frames + lenses earn | Safer default. Future products consciously enabled |

**5 Future-proofing Slots:**
- P1 — Multi-program-per-tenant
- P2 — Cross-tenant pooling
- P3 — AI personalization
- P4 — Manual VIP tier override
- P5 — Multi-currency

**Lessons:**

1. **Anti-Access pattern check.** When user describes legacy process, classify: (a) genuine business need or (b) workaround for tech limitation. (b) should NOT inherit. D13 was textbook.
2. **"Basic spec" → "comprehensive Brief" expansion is a delivered service.** Basic captures intent; Brief captures implementation reality (5-10x expansion).
3. **Number tuning is separate from architecture.** Sequential: architecture first, numbers second.
4. **Don't anchor on first proposed numbers.** Daniel adjusted Silver 3→4%, scale 50→30%, both improved the design.
5. **Settings panel was missed initially.** New rule: any Brief with Pattern P19 must include settings-panel sketch by default.
6. **Customer-visible language matters.** Sketches use customer Hebrew, not engineering terms.

## 2026-05-12 — M13 Brief Amendment — D14 (basic-free tier) added

**Event:** Targeted amendment to the sealed M13 Brief adding `basic-free` membership tier. Documentation-only — no code, no DB, no schema, no sketch changes. 5 files updated via Full-Auto Pipeline in a single chat.

**Why:** During M9 D24 (2026-05-10), Architect identified a structural gap — M9's compensation engine has no place to land a credit for a non-member customer. The 13 sealed M13 decisions all assumed paying members; there was no slot for an auto-created credits-only membership type. Same gap applies to the future Referral slot (P21). Closing this gap before M13 SPECs begin avoids embedding the assumption in code.

**Daniel directive (2026-05-10, in M9 sealing session):** "M13 needs a tier slot for compensation-credit holders who aren't paying members yet. Add it before M9 build starts so the M9-M13 contract is clean."

**SPEC:** `modules/Module 13 - Loyalty Club/architecture-brief/M13_BRIEF_AMENDMENT_BRIEF.md` (architect-authored brief, 5 file updates declared in §3).

**D14 — Basic-Free Tier (locked decision):**

| Field | Value |
|---|---|
| Slug | `basic-free` |
| Creation trigger | Auto on first qualifying event: M9 compensation OR Referral bonus (slot only at LIVE day-1) |
| Fee | None |
| Accrual rate | 0% all categories |
| Welcome bonus | Not issued |
| Family pool | Not joined |
| Promotion/downgrade engine | Excluded |
| Credit redemption | Same M7 Redeem Engine as paid tiers |
| Upgrade path | Customer pays via enrollment page → `tier_id` flips to paid tier; **credit balance preserved** |
| Schema impact | None — `loyalty_tier` config row only, added at M13 seed time |
| Exists at LIVE day-1 | No — created on-demand only |

**Architecture verdict:** D14 is fully SaaS-clean. Other tenants can disable basic-free by setting `is_active=false` on their `loyalty_tier` row where `slug='basic-free'`. Zero code change to disable; zero code change to rename for a tenant who wants different terminology. Pattern P19 (config table, not enum) carries this — basic-free is just one more row.

**Cross-module impact:**
- **M9 (Lab/KDS)** — M9's `compensation_issue` flow will now call `loyalty_ensure_basic_free_membership(customer_id, compensation_amount, source='m9_compensation')` before inserting the `loyalty_credit_transaction`. This RPC is one-shot idempotent — if the customer is already a member of any tier, it skips creation. M9 build SPEC must reference this contract.
- **M5 (Customers)** — no impact. Customer card S1 will show "חברות: Basic-Free (קרדיט בלבד)" for basic-free members. No structural change to S1.
- **M7 (Orders)** — no impact. Redeem Engine doesn't care which tier issued the credit.
- **M3 (Storefront)** — `/loyalty-club/` enrollment page handles the upgrade-from-basic-free flow same as enrollment from anonymous (single form, `loyalty_membership.tier_id` flips, `annual_fee_paid_at = now()`).

**Lessons:**

1. **Amendments are first-class.** Sealing a Brief doesn't mean it's frozen — when a downstream module surfaces a gap, a targeted amendment is the right vehicle. Don't re-open the full Brief sealing process for one decision. The amendment is itself a SPEC with its own success criteria.
2. **Cross-module gap discovery happens during the second-touching module's sealing.** M9 was the module that surfaced the M13 gap because M9's compensation flow needed an M13 contract that didn't exist. Architect's job is to catch these during the second sealing and close them before code starts, not during code.
3. **Brief amendments use the same skill stack as build SPECs.** Full-Auto Pipeline ran the amendment in one chat. No special "amendment mode" needed — the existing pipeline handles it.
