## 2026-05-07 — M15 Architecture Brief sealed (11 locked decisions)

**Context:** M15 = current queue inside the shop (walk-in + arrived appointments). NOT pre-scheduling (that's M14). Domain-neutral (any business with a walk-in queue: optical, salon, healthcare, government office).

**Brief structure:** 1 entity + 1 config table + tenant_settings keys, 3 dedicated Views, 5 RPCs, 4 states (waiting / in_progress / done / removed). UI = embedded panel inside M14 calendar (NOT a separate screen).

**Locked decisions (full list in Brief §9):**

1. M15 = separate module from M14 (Daniel directive — not merged).
2. M15 UI = embedded panel inside M14 calendar screen, NOT separate screen.
3. Adding to queue is MANUAL only day-1 (NOT auto from appointments).
4. 4 states: `waiting`, `in_progress`, `done`, `removed`.
5. Atomic sync against `appointment.status` (Pattern 14 — new in v1).
6. One shared queue with optional `preferred_resource_id`.
7. Day-1 = internal-only. Public surface = deferred.
8. Auto-save history. NO daily reset.
9. Wait time auto-calculated with 2 color thresholds (configurable per-tenant).
10. Pattern 13 on `queue_removal_reasons` (system + tenant rows).
11. Pattern 14 NEW (cross-module atomic state sync via RPC).

**Key cross-module patterns:**

- **Pattern 14 — Cross-module atomic state sync via RPC (introduced in M15 Brief §4.4):** When two entities in different modules represent the same business event in two models, their state transitions MUST be synced atomically. Implementation: a single RPC in the leading module performs both UPDATEs in one transaction; if either fails, both rollback. M15 leads (the physical walk-in event is the trigger), so `start_queue_entry` + `complete_queue_entry` RPCs each perform `queue_entries.status` UPDATE + `appointments.status` UPDATE atomically. Future use case documented: M7 ↔ M8 lock-on-order-close (when order closes, the final linked payment must lock).

- **Embedded-panel UI pattern (introduced in M15 Brief §7):** When module B is closely related to module A and shares a primary entity, B's UI lives as an embedded panel inside A's primary screen — not as a separate screen. M15's UI = panel inside M14 calendar (top-right or bottom). Trade-off: B loses its own URL but gains immediate context. Suitable when: (a) B has < 5 interactions / day per user; (b) the operator always opens B in the context of A; (c) A has unused screen real-estate. Counter-example: M11 reports are their own screen (different primary user, different mental context).

## 2026-05-14 — Module Close Ceremony — M15 (backlog batch close)

**Patterns reinforced by this batch close:**

1. **P41 — Manual-now-with-auto-twin-hook.** M15's queue-add is MANUAL only day-1. Auto-add from M14 (e.g., automatically promote arrived appointments into the queue) is deferred. The RPC `add_to_queue` is the fact-emitting function — both manual (today, via UI button) and auto (tomorrow, via M14 trigger or M12 rule) call the same RPC. Combined with M7 (5 manual forms) + M12 (manual templates) + M14 (`send_notification` checkbox), this becomes the 4-strike trigger for **P41** in SKILL.md.

2. **Pattern 14 — Cross-module atomic state sync via RPC.** M15 introduced this as a module-internal pattern (queue_entry.status ↔ appointment.status). Single instance + transformational. NOT promoted to a Pn yet — kept as Brief-internal "Pattern 14" pending a second use case (M7 ↔ M8 lock-on-close is documented in Brief §4.4 but not yet implemented). Re-evaluate at first M7 build SPEC. The pattern itself is sound; the question is whether a NEW Pn is needed or whether it's a sub-case of Iron Rule 16 (contracts between modules) + atomic-transaction discipline.

3. **Embedded-panel UI pattern (M15 inside M14 calendar)** — When module B is closely related to module A and shares a primary entity, B's UI lives as an embedded panel inside A's primary screen, not as a separate screen. Captured here; NOT promoted to a Pn yet — single-instance; re-evaluate if M9 lab-board ends up as an embedded panel in M7 order screen (likely candidate — both modules share sub_order as primary entity).

4. **Internal-day-1 / public-surface-deferred** — M15 ships internal-only at day-1 (`queue.show_to_public` toggle defaults to false). Public surface (kiosk display, take-a-number screen) is deferred. This pattern (P17 foundation-first) is already promoted; M15 reinforces it.

**Lessons NOT promoted (kept module-internal):**

- "Walk-ins with `appointment_id != NULL` AND `status='arrived'` get top priority in queue ordering" — single-instance priority rule.
- "Duplicate-queue-entry check prevents same customer in queue twice on same day" — single-instance integrity check.
- "Wait-time auto-calculated with 2 thresholds (yellow + red), configurable per-tenant" — instance of P40 (configurable-per-tenant default), already covered.
- "Auto-close-after-X-hours = deferred (manual 'finish all in_progress of yesterday' shortcut day-1)" — single-instance operational decision.

Contributed 1 strike to **P41** (4-strike promotion). **Pattern 14** (cross-module atomic state sync) introduced as module-internal — held back from skill promotion pending second use case. 2 single-instance patterns (embedded-panel UI, internal-day-1) noted for future cross-module check.
