## 2026-05-24 — WhatsApp SPEC 6 re-planned: Dialog360 (official WABA) integration

**Situation:** Daniel's correction: WhatsApp marketing sends MUST go through Dialog360, NOT Green API. Green API is not built for bulk marketing — 1000+ recipients = number banned. Dialog360 is the compliant path: official WABA, pre-approved templates, legal bulk sending. The M12 Communications Brief (sealed 2026-05-09, Decision #1) already specified this choice with a direct EF→360dialog REST API path (bypasses Make entirely).

**Re-assessed architecture (verified from M12 Brief + code):**

The M12 Brief defines:
- `channel_configs` table: per-tenant, per-channel vendor config with encrypted JSONB credentials (WABA ID, API keys). Iron Rule 19 compliant.
- `module_channel_routing` table: per-module override of channel defaults.
- WhatsApp dispatch: **direct EF → 360dialog REST API** — NOT through Make. Make stays only for SMS (Global SMS) and Email.
- Specific WABA number: +972 53-434-7265, described as undergoing migration from Meta-direct to 360dialog.

**This changes SPEC 6 significantly from the prior "validation lift" assessment:**

1. **New vendor integration path** — direct HTTP from send-message EF to Dialog360 API (auth, send-template-message, check-delivery-status). This is a new dispatch path alongside the existing Make webhook path. Not a simple channel string change.

2. **WhatsApp template pre-approval** — Dialog360/Meta require all marketing templates to be submitted and approved BEFORE they can be sent. Approval cycle: typically 24-48 hours, sometimes longer for marketing category. This is a **lead-time dependency** that exists outside the code pipeline — templates must be submitted to Dialog360 early, independent of ERP code work.

3. **Template model differs from SMS/email** — WhatsApp Business API templates have structured components (header, body, footer, buttons) and are identified by template_name + language_code, not free-form body text. The CRM template model needs to accommodate this (either a WhatsApp-specific body format or a separate template registration flow that maps CRM templates to Dialog360 template names).

4. **Consent model** — WhatsApp Business Policy requires explicit user opt-in for marketing messages outside the 24-hour service window. For utility messages (order updates, delivery notifications), opt-in is implicit. For marketing templates (the primary use case here), explicit opt-in is mandatory. Need a consent flag on the lead record.

5. **Per-tenant config** — `channel_configs` table with `provider='dialog360'`, `provider_credentials` (encrypted JSONB: `{ api_key, waba_id, phone_number_id }`). Iron Rule 19.

**My recommendation (SPEC 6 decomposition — 2 sub-SPECs):**

SPEC 6 is heavier than initially assessed. Recommend decomposing into:

**SPEC 6A: M4_WHATSAPP_CHANNEL_INFRA** (ERP-side, 2-3 sessions)
- `channel_configs` table (per-tenant, per-channel, encrypted credentials — from M12 Brief)
- send-message EF: accept channel='whatsapp', add Dialog360 dispatch path (direct HTTP to 360dialog REST API alongside existing Make path for SMS/email)
- dispatch-queue EF: WhatsApp throttling config (whatsapp_throttle_ms, whatsapp_daily_cap from SPEC 2's crm_dispatch_config)
- crm_message_templates: allow channel='whatsapp', add whatsapp_template_name field (maps CRM template → Dialog360 pre-approved template name)
- WhatsApp test-mode allowlist
- Consent flag on crm_leads (marketing_whatsapp_opt_in boolean)
- Short links: W-prefix convention activation

**SPEC 6B: M4_WHATSAPP_TEMPLATES_AND_LAUNCH** (ops + verification, 1 session)
