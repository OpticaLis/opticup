## 2026-05-24 — 3-way WhatsApp path comparison: Dialog360 vs Make Cloud API vs Direct Cloud API

**Situation:** Daniel discovered Make has a native "WhatsApp Business Cloud" module connecting to Meta's official Cloud API. Three paths now on the table. Daniel's priorities (ranked): (1) WhatsApp is MANDATORY with FUTURE deep integration (two-way inbox, customer-card, automation); (2) compliant for marketing to 1000+; (3) cost secondary to compliance + future-fit; (4) ~1 month to first 5K+ campaign.

**Head-to-head assessment:**

### Path A: Dialog360 (BSP) — direct EF → 360dialog REST API

| Dimension | Assessment |
|---|---|
| Compliance | Official WABA BSP, Meta-certified. Pre-approved template sending. Legal for 1000+ marketing. |
| Cost | ~$59-119/mo/number + Meta per-conversation fees (~$0.04-0.08 marketing, ~$0.01-0.02 utility, Israel). |
| Two-way inbox | **Decisive advantage:** Coexistence Mode + `smb_message_echoes` webhook. Staff WhatsApp Business app stays live on their phone. Every staff-initiated reply auto-mirrors into the system inbox — zero blind spots. This is the M12 Brief's day-1 requirement. |
| Template approval | Via Dialog360 dashboard (submits to Meta on your behalf). Streamlined. |
| EF integration | Direct HTTP to 360dialog REST API. Clean channel abstraction. No Make dependency. |
| Vendor lock-in | BSP-level lock-in. Migration to another BSP or direct Meta is possible but requires WABA number transfer (~1-2 weeks). |
| Staff phone coexistence | YES — the defining feature. Staff keeps using WhatsApp Business app daily; API runs in parallel. |

### Path B: Meta Cloud API via Make's "WhatsApp Business Cloud" module

| Dimension | Assessment |
|---|---|
| Compliance | Official Meta API (through Make). Compliant for marketing. |
| Cost | No BSP fee ($59-119 saved). Meta per-conversation fees same as A/C. Make subscription (already exists). |
| Two-way inbox | **Fatal gap:** Make's module is primarily outbound. Inbound webhook handling is limited — Make scenarios can receive webhooks but are NOT a real-time inbox system. Building the M12 two-way inbox through Make scenarios would be fragile, slow, and would need to be replaced anyway. |
| Template approval | Via Meta Business Manager directly (more manual than Dialog360 dashboard). |
| EF integration | EF → Make webhook → Make module → Meta API. Adds latency + Make as a critical dependency for a core channel. If Make has downtime, WhatsApp stops. |
| Vendor lock-in | Make becomes critical infrastructure. Migration to direct API = rewrite the dispatch path (same work as Path A/C from scratch). |
| Staff phone coexistence | Uncertain — depends on Make's module implementation. No smb_message_echoes (BSP feature). Staff phone messages invisible to system. |

### Path C: Meta Cloud API DIRECT from EF (no Make, no BSP)

| Dimension | Assessment |
|---|---|
| Compliance | Official Meta API. Compliant for marketing. |
| Cost | Cheapest: Meta per-conversation fees only. No BSP fee, no Make dependency. |
| Two-way inbox | Possible via Meta webhooks (register a webhook URL, receive inbound messages). But NO smb_message_echoes — if staff sends a message from the WhatsApp Business app on their phone, the system doesn't see it. Inbox has blind spots for staff-initiated replies. |
| Template approval | Via Meta Business Manager directly. |
| EF integration | Direct HTTP to Meta's graph.facebook.com/v18.0. Clean. More complex webhook management (Meta sends raw webhooks, we handle routing/retry/verification). |
| Vendor lock-in | Lowest — direct Meta relationship, no intermediary. |
| Staff phone coexistence | Partial since Meta's 2024 "phone number sharing" update. But without smb_message_echoes, staff replies from the Business app are invisible to the API system. |

**The decisive factor: staff phone coexistence + complete inbox.**

Prizma's staff uses WhatsApp Business app on their phone DAILY for customer communication. The M12 Brief explicitly states: *"WhatsApp is the day-1 critical-path channel — without it, the LIVE cutover regresses Prizma's daily operations."* The `smb_message_echoes` webhook (a BSP feature, not available in direct Meta API or Make) automatically mirrors every staff reply into the system inbox. Without it:
- Path B (Make): staff replies invisible. Dead end for M12 inbox. Temporary path that creates migration debt.
- Path C (Direct): staff replies invisible. Would need a BSP later for the inbox anyway. Saves $59-119/mo but at the cost of blind spots + future migration.
- Path A (Dialog360): staff replies visible via smb_message_echoes. Complete inbox from day 1. The $59-119/mo is negligible vs. the operational value of zero blind spots.

**My recommendation (ranked):**

**1. Path A: Dialog360 — CONFIRMED as the right choice.** The M12 Brief's decision stands and is strengthened by the comparison. Coexistence Mode + smb_message_echoes is a capability that neither Make nor direct Meta API can replicate. Given Daniel's priority #1 (future deep integration, two-way inbox), this is the only path that doesn't create migration debt. The $59-119/mo is the cost of a complete, production-grade WhatsApp channel with zero staff disruption.

**2. Path C: Direct Cloud API — viable ONLY if the two-way inbox is deprioritized** (not Daniel's stated priority). Saves the BSP fee but creates an inbox blind spot that would need a BSP to close later.

**3. Path B: Make Cloud API — NOT recommended.** Adds Make as a critical dependency for WhatsApp, offers no path to the two-way inbox, and would need to be replaced when M12 inbox is built. A dead end.
