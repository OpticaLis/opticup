## 2026-05-24 — WhatsApp as third M4 channel: assessment + sequencing

**Situation:** Daniel says "I must send WhatsApp to customers" — urgent, wants it before/around the first 5K+ campaign (~1 month). M4 today has email + SMS only. Green API is already in use via Make for QR-registration and catalog flows, but the CRM dispatch pipeline (send-message + dispatch-queue) is hardcoded to SMS + email.

**Assessment (verified from code):**

The dispatch architecture is: `dispatch-queue EF → send-message EF → Make webhook → Make scenario routes by channel → vendor`. The Make payload already includes `{ channel, recipient_phone, body, subject }`. This means adding WhatsApp is primarily a validation/schema lift, not an architectural overhaul:

1. **send-message EF** — hardcoded `channel !== 'sms' && channel !== 'email'` guard at line 119. Change to accept `'whatsapp'`. Add recipient validation (phone required, like SMS). Add WhatsApp allowlist for test-mode (same pattern as SMS/email allowlists).
2. **Make scenario** — needs a WhatsApp route (Green API sendMessage). This is a Make-side config change, not ERP code. Daniel/ops can configure it.
3. **crm_message_templates** — allow `channel='whatsapp'`. Create Hebrew WhatsApp templates (body format: plain text, similar to SMS but can include rich formatting).
4. **dispatch-queue EF** — add WhatsApp throttling (configurable, alongside SMS/email throttles). Green API rate limit is ~1 msg/sec.
5. **Consent** — WhatsApp Business Policy requires user opt-in for marketing messages outside the 24-hour service window. Green API (unofficial) doesn't enforce this technically, but account-ban risk exists at scale. For now, practical approach: send only to leads who have a phone number + have not unsubscribed (same as SMS). Formal opt-in flow is a separate future SPEC.
6. **Short links** — `W` prefix already reserved in the channel convention.
7. **No Green API credentials in our DB** — `ui_config` has `whatsapp_phone_e164` (the number) but no `green_api_instance_id` or `green_api_token`. The Make scenario handles Green API auth directly — our EF never calls Green API; it calls Make.

**My recommendation — SEPARATE TRACK, not bundled with scale SPECs:**

The scale SPECs (queue-lifecycle, throughput, screen-audit) are infrastructure that benefits ALL channels. WhatsApp is a new dispatch path. Different concerns, different risk profiles. Bundling would delay the pre-10K-blocking work.

However, SPEC 2 (dispatch-throughput) MUST be WhatsApp-aware in its design: the `crm_dispatch_config` table should include `whatsapp_throttle_ms` and `whatsapp_daily_cap` columns from day one, even though WhatsApp dispatch isn't implemented yet. Zero extra effort — just add the columns. When the WhatsApp SPEC lands, the config surface is already there.

**Recommended sequence:**

```
Week 1-2: SPEC 1 (queue lifecycle) + SPEC 2 (throughput — 3-channel config design)
Week 2-3: SPEC 3 (screen audit) ‖ SPEC 6 (WhatsApp channel — can run in parallel)
Week 3-4: SPEC 6 completes (templates + testing + Make scenario)
```

WhatsApp as SPEC 6 (new, added to the Master Plan):

- **Scope:** EF validation lift (accept 'whatsapp'), WhatsApp allowlist, template schema expansion, WhatsApp templates for existing automation flows, dispatch-queue WhatsApp throttle wiring, short-link W-prefix convention activation.
- **Make-side:** Daniel/ops configure the WhatsApp route in Make scenario 9104395 pointing to Green API.
- **Vendor:** Green API via Make (already familiar, fastest path). Migrate to WhatsApp Business API later if volume justifies.
- **Estimated effort:** 1-2 sessions (ERP-side is small; Make-side is ops work).

**Blocking questions for Daniel:**
1. The Make scenario (9104395) that handles SMS + email dispatch — does it already have a WhatsApp route, or does one need to be added? (Architect cannot inspect Make scenarios directly.)
2. Is the existing Green API account (used for QR/catalog) capable of outbound marketing messages, or is it limited to inbound-initiated conversations?
3. Consent model: is it acceptable for now to send WhatsApp to all leads with a phone number (same gate as SMS), or does Daniel want an explicit WhatsApp opt-in before the first send?

**Daniel's response:** (pending)

**Lesson:** When the dispatch architecture is webhook-based with channel routing at the webhook consumer (Make), adding a new channel is primarily a validation + config lift, not a re-architecture. The heaviest work is vendor-specific (Make scenario config, template authoring, consent model) — not ERP code.
