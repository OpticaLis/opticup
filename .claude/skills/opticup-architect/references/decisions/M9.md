**Lessons:**

1. **"Old decision" must be reviewed when scope reframes.** The "M9 extends shipments" decision (Mar 2026) was made before McDonalds-System framing. Architectural assumptions that predate the use-case discovery deserve a fresh look. Pattern: when user reframes scope dramatically (here: "lab is just shipping" → "lab is the satisfaction system"), reopen previously-locked architectural decisions automatically.

2. **Sketches surface real constraints.** Several decisions changed mid-sketch when the visual confronted theory: incoming-box-full-entity (initially placeholder), 1:N return mapping (initially 1:1), 3-color escalation matched to category SLAs (not absolute time). Sketching forces constraints to surface.

3. **Manager max-addition is additive, not absolute.** Daniel correction. Format: "compensation = defined + manager_can_add_up_to_X". Most product owners think additively when adjusting recommendations.

4. **Per-tenant-config + per-tenant-defaults pattern works at scale.** M9 has 7 categories × 5 thresholds × 2 clocks = 70 config values per-tenant, plus shipping boxes types, damage reasons, courier list. All managed via tenant settings panel (P33 — settings sketch mandatory). This is the SaaS-clean shape.

5. **Replacing legacy patterns is OK when underlying tech is better.** M9 D2 overturned year-old "extends shipments" decision. Old decisions are not sacred when reframing reveals deeper truth. (Aligned with Pattern P32 — anti-legacy-pattern check.)

## Skill improvement proposals (apply to opticup-architect SKILL.md)

**Proposal 1 — Sketch-Before-Brief is now the law (P34 already promoted).** Reaffirmed: M9 had 4 separate sketch documents created BEFORE the Brief, each with 3 alternatives + recommendation banner. The Brief at the end was straightforward to write because all decisions were already validated visually.

**Proposal 2 — When user reframes scope dramatically, automatically reopen previously-locked architectural decisions.** M9 D2 (overturning "extends shipments") was a critical save. Could have shipped wrong if I'd just executed the old decision.

**Proposal 3 — When designing config-heavy modules (P19 + P33), build the Settings sketch before the operational sketch.** I built operational first (KDS) and Settings last; would have caught the M1 ↔ M9 supplier sync question earlier if Settings had been first.

**Proposal 4 — M9 introduced "manager_max_addition" as an additive cap.** Generalize: when an owner sets limits on subordinate's authority, the limit is usually expressed as an addition over recommendation, not as an absolute. This is a UX pattern worth promoting.
