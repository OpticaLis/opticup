## 2026-05-06 — Consent model: 4 independent flags + active-only re-subscription


**Situation:** After collapsing leads into customers (lifecycle_stage), the question of marketing consent across customer module vs CRM module surfaced. Many existing customers also register for campaigns; many leads convert to customers.
**My recommendation (final, after Daniel iteration):** Four independent consent flags per person:
  1. customer_marketing_consent (Prizma promotions to customers)
  2. customer_operational_consent (exam reminders, glasses-ready notices)
  3. crm_marketing_consent (campaign promotional content)
  4. crm_operational_consent (event details for events they registered to)

Migration defaults:
- 5,028 OpticPlus customers: customer_operational_consent=opted_in (default-on for operational, expected behavior). Other 3 flags=opted_out.
- 1158 leads: all 4 flags=opted_out (until they sign explicit consent).

Re-subscription rule: if person opts out of CRM marketing and later becomes a customer, they DO NOT auto-re-subscribe to CRM marketing. They must actively contact CS to re-enable. Customer-side flags are independent of CRM-side flags. NO module overrides another's consent.
**Daniel's response:** Agreed.
**Reason for agreement:** Active-consent only (matches Israeli privacy law direction + ethical stance). Module independence prevents accidental re-enrollment.
**Lesson 1:** Consent is per-domain, not per-person. Customer module and CRM module each have their own consent pair (marketing+operational). 4 flags total, not 2.
**Lesson 2:** Default-on for "operational" is acceptable for existing-customer migration. Default-off for everything else. This matches user expectation (existing customers expect exam reminders).
**Lesson 3:** Re-enrollment after opt-out is ALWAYS active (manual CS action). Never automatic on lifecycle change. This protects the user trust and is legally cleaner.

## 2026-05-06 — M5 households: skeleton entity, optional FK, phone is family-shared OPTIONALLY


**Situation:** Should "household" be a flag, an entity, or a relationship graph? And how does phone uniqueness interact?
**My recommendation (after Daniel's "simple now, flexible later" + "phone unique except in families" directive):** Skeleton `households` entity (3 fields: id, tenant_id, primary_customer_id) + nullable `customers.household_id`. Phone uniqueness was initially proposed as `UNIQUE (phone) WHERE household_id IS NULL`.
**Daniel's correction:** Phone-sharing within a family is the EXCEPTION, not the rule. Most family members have their own phones. Schema must not assume shared phones inside a household.
**Reason for correction:** Real-world reality of optical clientele — adult family members have individual phones; only edge cases (a parent paying for a teenager whose phone is the parent's) share.
**Lesson 1:** Don't infer schema constraints from edge cases. The 90% case (each family member = own phone, household = address/billing/loyalty unit) is the design point. Family-shared phone is the rare exception, handled as an exception, not a baseline.
**Lesson 2:** Phone uniqueness should be `UNIQUE (phone, tenant_id)` BUT with the ability to override per-pair when a real shared phone exists — handled at insert/UI level, not as a structural rule. The household entity exists for OTHER reasons (loyalty pooling, shared billing, family marketing) — NOT primarily to bypass phone uniqueness.
**Pattern:** When user gives a justification ("X because Y"), check if Y is the *primary* reason or just one symptom. If primary reason ≠ what I assumed, the design changes shape.

## 2026-05-07 — M5 customers-list screen: 3 sketches → Split Workspace approved


**Situation:** Daniel showed his original Access main-screen sketch and asked for 3 different sketches for the customer-management screen with direct links to other modules (inventory, queue, quick-task, order-pickup, repair, club-members, etc.).
**Initial mistake:** I proposed splitting "daily ops dashboard" from "customer search" as two screens. Daniel pushed back — he already has a main Dashboard (the 12-tile screen with all modules) + an Access-style search popup. Two extra screens would be redundant.
**Correction:** I reversed — one screen, with quick-search up-top and an "Advanced Search" button that opens a filter panel (mirrors the Access pattern). One screen, two roles.
**My recommendation:** Built 3 sketches representing 3 different design philosophies:
1. Command Center — horizontal action dock + big customer list + live status side-card
2. Split Workspace — fixed left nav (categorized actions+modules) + rich main list with filter pills
3. Daily Stream — Kanban of customer-states (today's exams / lab / ready-pickup / tasks+repairs)

Recommended #2 (Split Workspace). Reason: most scalable as more modules join — left nav absorbs them without crowding the header. List has room to be the dominant element. Sketch 3's Kanban can later be added as an internal tab on top of Sketch 2.
**Daniel's response:** Agreed — "סקיצה 2 - מאושרת".
**Reason for agreement:** Implicit; aligned with the recommendation.

**Lesson 1 (process):** When Daniel asks for "3 different sketches", the value comes from 3 *philosophies* not 3 *visual variations*. Each sketch should have a distinct organizing principle (action-dock vs side-nav vs kanban) — this gives Daniel a real choice rather than picking a color.
**Lesson 2 (architecture):** "Don't add screens unless absolutely necessary" is a Daniel preference. The first instinct of separating concerns into multiple screens is often wrong — modern UIs use overlays, panels, and filters within one screen. Future module screens: default to ONE screen with progressive disclosure (advanced search as panel, kanban as tab, etc.) before proposing a separate screen.
**Lesson 3 (strategic):** When proposing screen separation, run the litmus: "Is the user moving between two contexts, or two views of the same context?" Two views = one screen with toggle/filter. Two contexts = two screens. Customer search and customer-list-view are two views of the same context — one screen.
