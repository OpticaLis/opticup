**Lesson 2:** When a previously-decided architecture turns out wrong mid-process, REVERSE IT IMMEDIATELY in the brief file. Don't compound the mistake by writing M7+ on top of the broken M4↔M5 boundary. Update M5 brief NOW. Note the change. Note the reason. Module Strategists should never see the broken version.
**Lesson 3:** Architectural symmetry-breakers come from real-world overlap stories, not from schema reasoning. ## 2026-05-07 — Correction: "Thanks" is order-level, not sub-order-level


**Situation:** I built v6 with "Thanks" as one of FOUR per-sub-order message buttons. Daniel corrected sharply.
**My error:** I conflated "all messages tied to order workflow" into a single per-sub-order grid. "Thanks" is a one-time event for the entire order — sent once after first payment, regardless of how many sub-orders exist. Per-sub-order messages are only "Sent for framing" and "Order ready" (each sub-order is delivered on its own timeline).
**Correction applied to v6:**
- "Thanks" badge moved to the top command bar (order-level), shown once with timestamp.
- Per-sub-order grid reduced from 4 buttons to 2: "Sent for framing" + "Order ready". A note clarifies that "Thanks" lives at order level.
**Reason:** The customer hears "Thanks for your order" once per visit, not once per sub-order. Spamming "thanks" four times for one purchase is wrong and would erode trust.
**Lesson:** When grouping actions, separate by their REAL granularity. "Per-order" vs "per-sub-order" is a hard line — putting an order-level action inside a per-sub-order block is a UX bug AND a potential duplicate-message bug. Before building any future grid of actions, explicitly tag each action with its granularity (order / sub-order / item) and group accordingly.
**Pattern:** Every message/event in the system belongs to exactly one granularity tier. Future modules: tag at design time.

## 2026-05-07 — M5 customers-list: Activity-first columns + tenant-configurable column set + dual-mode search


**Situation:** After approving Sketch 2 (Split Workspace), needed to lock 3 sub-decisions on the main list:
1. What columns appear (identity-first vs activity-first).
2. Are columns fixed or configurable.
3. Search architecture (one search vs quick + advanced).

**Decisions reached:**

1. **Activity-first columns** (Approach B). The middle of the list shows what's *happening* with the customer (active status, pending order, open task, debt) — not who they are (age, kupat-cholim). Identity lives inside the customer card, which still opens on click. Reason: 80% of daily list-glances are looking for an action, not for identity.

   Initial mistake: I framed the recommendation poorly — Daniel asked "are you saying clicking a row should NOT open the card?". I had to clarify that click-to-open stays unchanged; the decision is only about the column content displayed BEFORE the click. Lesson logged below.

2. **Tenant-configurable column set.** Daniel's directive: "כל TENANT יכול להעדיף את זה בצורה אחרת". Final structure:
   - **Fixed columns (cannot be hidden):** name + phone. These are the anchors; without them the staff can't identify the customer at all.
   - **Configurable columns (3-5 columns, default = activity-first):** active status, active order, task/repair, debt balance, club membership. Tenant admin picks which ones show and in what order, from a closed list of options that ALSO includes identity columns (kupa, age, language, ID#) — so a tenant who prefers "Approach A" can build it via configuration.
   - **Storage:** `tenant_settings` (or equivalent), not code. Iron Rule 19 (configuration over code) applies.
   - **Per-user vs per-tenant:** tenant-level only for now. Per-user can be added later if there's demand.

3. **Dual-mode search.** Quick-search bar (smart, single field — auto-detects name vs phone vs ID# vs order#) sits at the top of the main area always. Advanced-search opens as a side panel with all 14+ Access-style parameters (name parts, ID, phone, address, city, kupa, exam dates, optometrist, Rx values like Sph/Cyl/Axis, "inactive customers", "un-numbered customers"). Reason: 95% of searches are "find Yossi Cohen" → one field solves in 2 seconds; advanced is for rare needs and shouldn't clutter the default screen.

**Daniel's responses:** Agreed to all three. Phone clarification on #2 came from Daniel: "חשוב לי שמספר הטלפון יהיה כתוב במקום כלשהו" — incorporated as a fixed column.

**Lesson 1 (communication):** When framing a binary recommendation (A vs B), do not assume Daniel maps the framing the same way I do. He misread "Activity-first" as "no-card-on-click" — a totally different change. Future binary recommendations: include a one-line scenario showing what the user *experiences*, not just what the columns *show*. "User opens screen, sees X. Clicks row, gets Y." This grounds the recommendation in flow, not in label.

**Lesson 2 (SaaS architecture):** Daniel's instinct to make UI choices configurable per-tenant is consistent across this whole project — and it should be the default assumption, not the exception. When designing any list, table, or screen layout, the first question is "would tenant #2 want this differently?" If yes, configurable. This is the practical application of the SaaS litmus test. Going forward, propose configurability proactively rather than waiting for Daniel to flag it.

**Lesson 3 (UX patterns):** The pattern "fixed anchor columns + configurable content columns" is general — it applies to every table in the system (orders list, prescriptions list, lab queue, etc.). The fixed anchors are whatever lets the user identify the row at all (usually 1-2 fields); everything else is content the tenant chooses. Codify in the design-conventions doc when it emerges.
