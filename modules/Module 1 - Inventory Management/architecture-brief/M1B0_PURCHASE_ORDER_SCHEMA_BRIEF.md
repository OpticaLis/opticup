## 1. Purpose

Phase 1A reviews surfaced that `purchase_order`, `purchase_order_line`, and `supplier_debt` were never shipped — even though three Phase 1B screens (PO, Active POs List, Goods Receipt) and decision D-M1-11 depend on them. The Strategic Review classified this as a 🔴 blocker.

This micro-SPEC ships **only** the PO + PO-line + supplier_debt schema plus the minimal RPCs that operate on them — **schema, no UI**. The 6 Phase 1B screens land in a subsequent SPEC, on top of this verified schema.

**Why a separate micro-SPEC and not part of Phase 1B:**

Phase 1A's "schema + UI in one SPEC" pattern produced a sealed schema that was never functionally exercised — the smoke was existential (table exists), not operational (RPCs work). The reviews caught it; the fix-SPEC made the lesson permanent. M1B0 keeps that discipline: **the new schema and its RPCs must pass a functional smoke on demo BEFORE any UI is built on top.**

**Scope is schema-only.** No screens. No JS modules. No HTML pages. No mockup changes. The 7 sealed mockups already accommodate this schema; they get wired in Phase 1B.

## 2. Scope — In

### Table #1 — `purchase_order`

A PO is the **intent to procure** from one supplier. Lifecycle: Draft → Sent → Partially received → Fully received → (Cancelled). Status enum is M1-internal (Iron Rule 19 — bounded accounting-semantic enum, not tenant-configurable).

Core columns (Module Strategist confirms exact types/nullability live against PG17 + ILS-only Day-1):

- `id UUID PK`
- `tenant_id UUID NOT NULL REFERENCES tenants(id)` (Iron Rule 14)
- `po_number TEXT NOT NULL` — sequential, generated by `next_po_number(p_tenant_id)` (Iron Rule 11 — atomic FOR UPDATE)
- `supplier_id UUID NOT NULL REFERENCES suppliers(id)` (existing table, M1 source of truth)
- `status TEXT NOT NULL DEFAULT 'draft'` with CHECK constraint over `('draft','sent','partial','fully_received','cancelled')`
- `ordered_at TIMESTAMPTZ NOT NULL DEFAULT now()`
- `sent_to_supplier_at TIMESTAMPTZ NULL`
- `expected_delivery_at DATE NULL` (per D-M1-10 reconciliation-agent schema readiness)
- `cancelled_at TIMESTAMPTZ NULL`
- `cancelled_reason TEXT NULL`
- `created_by UUID NULL` (employees.id; SET NULL on delete)
- `notes TEXT NULL` (optic-internal)
- `is_deleted BOOLEAN NOT NULL DEFAULT false` (Iron Rule 3 — soft delete)
- `deleted_at TIMESTAMPTZ NULL`, `deleted_by UUID NULL`
- `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`

Tenant-scoped UNIQUE: `(tenant_id, po_number) WHERE is_deleted = false`.

RLS: canonical 2-policy (`service_bypass` + `tenant_isolation` JWT-claim).

Indexes:
- Single-column `tenant_id` (RLS hot path)
- `(tenant_id, supplier_id, status) WHERE is_deleted = false` (Active POs List screen filter)
- `(tenant_id, status, ordered_at DESC) WHERE is_deleted = false` (default sort)
- `(tenant_id, expected_delivery_at) WHERE status IN ('sent','partial') AND is_deleted = false` (overdue-PO sentinel)

**Naming divergence note:** The legacy frames-era `purchase_orders` table (plural) exists in `docs/GLOBAL_SCHEMA.sql`. Phase 1A resolved the parallel `goods_receipts` (legacy) vs `purchase_receipt` (lens) question with option (c) — divergence. **M1B0 inherits the same resolution:** legacy `purchase_orders` stays untouched for frames; new `purchase_order` (singular) is the lens-era table. SPEC §0 baselines this explicitly so the executor doesn't try to `ALTER` the legacy table.

### Table #2 — `purchase_order_line`

Lines belong to one PO. Each line is one variant being ordered. Three sources per D-M1-07:

- **Stock line** — reorder for inventory; `sale_order_id IS NULL`.
- **Custom-per-customer line** — ordered for a specific M7 sale; `sale_order_id NOT NULL` (FK to future `sale_order(id)`, defer FK clause until M7 ships its table — same pattern Phase 1A used for `lab_jobs.purchase_receipt_id`).
- **Manual line** — free-form (e.g., supplies); `sale_order_id IS NULL`.

Core columns (Module Strategist confirms live):

- `id UUID PK`
- `tenant_id UUID NOT NULL` (Iron Rule 14, defense-in-depth on writes)
- `purchase_order_id UUID NOT NULL REFERENCES purchase_order(id) ON DELETE RESTRICT`
- `line_number INT NOT NULL` (1-based, contiguous within PO)
- `source TEXT NOT NULL` CHECK in `('stock','custom_per_customer','manual')`
- `variant_id UUID NULL REFERENCES lens_variant(id) ON DELETE RESTRICT` (null only for `source='manual'`)
- `sale_order_id UUID NULL` (no FK clause yet — see note below; for `source='custom_per_customer'` only)
- `sph NUMERIC(5,2) NULL` / `cyl NUMERIC(5,2) NULL` / `add_value NUMERIC(4,2) NULL` (for `source='custom_per_customer'`; null for stock/manual unless variant-encoded)
- `manual_description TEXT NULL` (for `source='manual'`)
- `qty_ordered INT NOT NULL CHECK (qty_ordered > 0)`
- `qty_received INT NOT NULL DEFAULT 0 CHECK (qty_received >= 0 AND qty_received <= qty_ordered)` — updated by GR RPCs (K2 lineage)
- `unit_cost NUMERIC(12,4) NOT NULL CHECK (unit_cost >= 0)`
- `currency_code TEXT NOT NULL DEFAULT 'ILS'` (no FK to currencies — matches Phase 1A pattern per M1A-SPEC-02 disposition)
- `vat_rate_id UUID NULL REFERENCES vat_rates(id)` (snapshot at line creation; Israel-only Day-1)
- `is_deleted BOOLEAN NOT NULL DEFAULT false`, `created_at`, `updated_at`

Tenant-scoped UNIQUE: `(tenant_id, purchase_order_id, line_number) WHERE is_deleted = false`.

RLS: canonical 2-policy.

Indexes:
- `tenant_id` (RLS)
- `(tenant_id, purchase_order_id)` (line lookup per PO)
- `(tenant_id, variant_id, source) WHERE source='custom_per_customer' AND is_deleted = false` (custom-line search)
- `(tenant_id, sale_order_id) WHERE sale_order_id IS NOT NULL` (M7 reverse lookup)

CHECK constraints (table-level, not column):
- `source='manual' → variant_id IS NULL AND manual_description IS NOT NULL`
- `source IN ('stock','custom_per_customer') → variant_id IS NOT NULL`
- `source='custom_per_customer' → sale_order_id IS NOT NULL`
- `source IN ('stock','manual') → sale_order_id IS NULL`

### Table #3 — `supplier_debt`

D-M1-11 is explicit: **debt is created at goods-receipt time, NOT at PO creation.** Accounting events follow physical events, not intent events. So this table is read-heavy at the GR screen + dashboard, write-light (one row per goods-receipt).

Core columns:

- `id UUID PK`
- `tenant_id UUID NOT NULL`
- `supplier_id UUID NOT NULL REFERENCES suppliers(id) ON DELETE RESTRICT`
- `purchase_receipt_id UUID NOT NULL REFERENCES purchase_receipt(id) ON DELETE RESTRICT`
- `delivery_note_number TEXT NOT NULL` (denormalized from receipt for fast joins; consistency enforced by trigger or RPC)
- `total_amount NUMERIC(12,2) NOT NULL CHECK (total_amount >= 0)` (sum of line amounts × (1 + vat_rate); snapshot at receipt close)
- `vat_amount NUMERIC(12,2) NOT NULL DEFAULT 0 CHECK (vat_amount >= 0)`
- `currency_code TEXT NOT NULL DEFAULT 'ILS'`
- `paid_amount NUMERIC(12,2) NOT NULL DEFAULT 0 CHECK (paid_amount >= 0)`
- `status TEXT NOT NULL DEFAULT 'open'` CHECK in `('open','partially_paid','paid','written_off')`
- `closed_at TIMESTAMPTZ NULL`
- `notes TEXT NULL`
- `is_deleted BOOLEAN NOT NULL DEFAULT false`, `created_at`, `updated_at`

Tenant-scoped UNIQUE: `(tenant_id, purchase_receipt_id) WHERE is_deleted = false` — one debt row per receipt.

CHECK: `paid_amount <= total_amount`.

RLS: canonical 2-policy.

Indexes:
- `tenant_id`
- `(tenant_id, supplier_id, status) WHERE is_deleted = false` (supplier debt panel — mockup #7 §"💰 חוב")
- `(tenant_id, status, created_at DESC)` (overdue debt sentinel)

**Scope cut:** payment-allocation table (payments → debt rows) is M8 (Payments) territory, NOT M1. M1's `supplier_debt.paid_amount` is updated by M8 RPCs that this SPEC does NOT ship. Phase 1B's GR screen reads `paid_amount` but does not write it. Day-1 the field stays 0 until M8 builds.

### `stock_lot.purchase_order_id` — back-pointer FK clause

Phase 1A added `stock_lot.purchase_order_id UUID` as a column but **without a FK clause** because `purchase_order` didn't exist. M1B0 adds the FK:

```sql
ALTER TABLE stock_lot
ADD CONSTRAINT stock_lot_purchase_order_fk
FOREIGN KEY (purchase_order_id) REFERENCES purchase_order(id) ON DELETE SET NULL;
```

Index: `(tenant_id, purchase_order_id) WHERE purchase_order_id IS NOT NULL` (reconciliation-agent traversal per D-M1-10).

### RPCs to ship (5)

All SECURITY DEFINER with `SET search_path = 'public'`, JWT-claim guard, `FOR UPDATE` where applicable, REVOKE EXECUTE FROM PUBLIC/anon, GRANT EXECUTE TO authenticated. Inherit ALL the discipline from `M1A_OPERATIONS_RPCS_FIX`.

**RPC #1 — `next_po_number(p_tenant_id UUID) RETURNS TEXT`**
Atomic per-tenant sequential generator. Format: `PO-NNNNNN` (zero-padded 6 digits). Uses the same MAX-based pattern as `next_lot_number` / `next_receipt_number` (Phase 1A precedent) — `FOR UPDATE` on `tenants(id)` to serialize, then `SELECT COALESCE(MAX(CAST(SUBSTRING(po_number FROM 4) AS INT)), 0) + 1 FROM purchase_order WHERE tenant_id = p_tenant_id`. Acknowledged brittle pattern (Reviewer A-4); accept consistency with Phase 1A.

**RPC #2 — `place_purchase_order(p_tenant_id, p_supplier_id, p_lines JSONB, p_expected_delivery_at, p_notes) RETURNS UUID`**
Atomic: validates supplier belongs to tenant; calls `next_po_number`; INSERTs `purchase_order(status='draft')`; INSERTs N `purchase_order_line` rows with `line_number` 1..N; validates each line's `source` CHECK; returns the new PO id. JWT-claim guard. Transactional.

**RPC #3 — `mark_po_sent(p_tenant_id, p_po_id) RETURNS VOID`**
Atomic: UPDATE `purchase_order SET status='sent', sent_to_supplier_at=now() WHERE id = p_po_id AND tenant_id = p_tenant_id AND status='draft'`. RAISE if not found OR wrong status. Per D-M1-07 manual-only Phase 1; the actual PDF/Excel export is Phase 1B UI work.

**RPC #4 — `cancel_purchase_order(p_tenant_id, p_po_id, p_reason TEXT) RETURNS VOID`**
Atomic: UPDATE to `status='cancelled', cancelled_at=now(), cancelled_reason=p_reason`. Only allowed from `status IN ('draft','sent')` — RAISE 42501 if from `partial` or `fully_received` (those need an explicit reversal flow, not this SPEC). Cascade: any open `purchase_order_line` rows stay (audit trail); no stock_lot is touched (none was created from a non-received PO).

**RPC #5 — `m1_create_supplier_debt_from_receipt(p_tenant_id, p_purchase_receipt_id, p_total_amount, p_vat_amount, p_currency_code) RETURNS UUID`**
Atomic: validates receipt belongs to tenant; computes nothing (caller passes totals); INSERTs one `supplier_debt` row with `status='open', paid_amount=0`. Idempotent via the UNIQUE `(tenant_id, purchase_receipt_id)` — `ON CONFLICT DO NOTHING` returning the existing id. **Called by `m1_create_receipt_from_box` (K2 RPC, Phase 1A) at end of receipt close** — this is the D-M1-11 wiring.

This last wiring requires a small extension of the existing K2 RPC body: after the existing `stock_lot` + `stock_movement` + `purchase_receipt_line` inserts, append a call to `m1_create_supplier_debt_from_receipt`. Module Strategist confirms via `pg_get_functiondef('m1_create_receipt_from_box'::regproc)` whether totals computation is already in the K2 body or needs to be added.

## 7. Iron Rules in Sharp Focus

Most likely to be tested:

- **Rule 1** — `place_purchase_order` is atomic (single transaction; multiple INSERTs).
- **Rule 11** — `next_po_number` uses FOR UPDATE on tenants(id) (Phase 1A precedent — brittle but consistent).
- **Rule 14** — `tenant_id NOT NULL` on every new table.
- **Rule 15** — canonical RLS pattern (JWT-claim USING, service_bypass + tenant_isolation). NO `auth.uid()`.
- **Rule 16** — modules talk only through contracts. `purchase_order_line.sale_order_id` has no FK Day-1 (M7 contract surface — deferred FK matches Phase 1A `lab_jobs.purchase_receipt_id` pattern).
- **Rule 18** — every UNIQUE includes `tenant_id`.
- **Rule 19** — `status` enum bounded by CHECK constraint (accounting-semantic, not tenant-configurable).
- **Rule 21** — singular `purchase_order` does NOT collide with plural `purchase_orders` (different tables, different scopes; resolution inherits Phase 1A Open Q1 option c).
- **Rule 22** — every `.insert()` / `.update()` in RPC bodies includes `tenant_id` in WHERE.
- **Rule 23** — no secrets.
- **Rule 31** — integrity gate exit 0 every commit.
- **Rule 32** — `Destructive Operations: None`. The `ALTER TABLE stock_lot ADD CONSTRAINT` is additive (not destructive). `CREATE OR REPLACE FUNCTION` for K2 extension is non-destructive.

## 9. Open Questions for the Module Strategist

Architect's recommendation in italics — Module Strategist may override only with evidence.

1. **`purchase_order_line.line_number INT` vs auto-incremented within PO (window function vs application-managed)?**
*Recommendation: application-managed inside `place_purchase_order` RPC — assign 1..N from the input JSONB array order.* Simple, no race (single transaction), matches mockup expectations.

2. **`supplier_debt.delivery_note_number` — denormalized from receipt, or always JOIN to receipt?**
*Recommendation: denormalized + enforced consistency via the `m1_create_supplier_debt_from_receipt` RPC (single writer).* Read-heavy access pattern (mockup #7 §"💰") justifies the cache; consistency is RPC-enforced.

3. **Should `cancel_purchase_order` soft-delete the PO or set status='cancelled'?**
*Recommendation: status='cancelled' (Day-1).* `is_deleted` reserved for genuine deletion (audit-trail hygiene). The cancelled state retains analytics value.

4. **`purchase_order.created_by` FK to employees — ON DELETE behavior?**
*Recommendation: ON DELETE SET NULL.* Audit-friendly: PO stays even if employee leaves.
