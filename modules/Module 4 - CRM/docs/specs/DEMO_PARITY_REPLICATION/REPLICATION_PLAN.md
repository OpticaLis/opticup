## 7. Special Handling Notes

### 7.1 Text-id tables (roles, permissions)

Schema: `id text NOT NULL` (no DEFAULT) + `PRIMARY KEY (id, tenant_id)`. The id IS the business key (e.g., `'admin'`, `'cashier'`, `'view_inventory'`, `'edit_leads'`).

INSERT column list MUST include `id` (not exclude it like the UUID-default tables). The INSERT semantics become:

```sql
INSERT INTO roles (id, name_he, description, is_system, created_at, tenant_id)
SELECT id, name_he, description, is_system, now(), '8d8cfa7e...'::uuid
FROM roles
WHERE tenant_id = '6ad0781b...'::uuid
  AND NOT EXISTS (SELECT 1 FROM roles d WHERE d.id = roles.id AND d.tenant_id = '8d8cfa7e...'::uuid);
```

UPDATE matches on `id` and updates `name_he`, `description`, `is_system`:

```sql
UPDATE roles d
SET name_he = p.name_he, description = p.description, is_system = p.is_system
FROM roles p
WHERE d.tenant_id = '8d8cfa7e...'::uuid
  AND p.tenant_id = '6ad0781b...'::uuid
  AND d.id = p.id
  AND md5(coalesce(d.name_he,'') || '|' || coalesce(d.description,'') || '|' || coalesce(d.is_system::text,''))
   IS DISTINCT FROM md5(coalesce(p.name_he,'') || '|' || coalesce(p.description,'') || '|' || coalesce(p.is_system::text,''));
```

Same pattern for `permissions` (with columns: id, module, action, name_he, description).

### 7.2 Composite-key table (role_permissions)

Schema: `role_id text, permission_id text, granted boolean, tenant_id uuid` + `PRIMARY KEY (role_id, permission_id, tenant_id)`. No `id`, no `created_at`, no `updated_at`.

Business key = `(role_id, permission_id)`. FK depends on `roles` + `permissions` existing for demo (composite FK with tenant_id). Must run AFTER roles + permissions in Phase 3.

```sql
INSERT INTO role_permissions (role_id, permission_id, granted, tenant_id)
SELECT role_id, permission_id, granted, '8d8cfa7e...'::uuid
FROM role_permissions
WHERE tenant_id = '6ad0781b...'::uuid
  AND NOT EXISTS (
    SELECT 1 FROM role_permissions d
    WHERE d.role_id = role_permissions.role_id
      AND d.permission_id = role_permissions.permission_id
      AND d.tenant_id = '8d8cfa7e...'::uuid
  );
```

UPDATE on `granted` flag if mismatched:

```sql
UPDATE role_permissions d
SET granted = p.granted
FROM role_permissions p
WHERE d.tenant_id = '8d8cfa7e...'::uuid
  AND p.tenant_id = '6ad0781b...'::uuid
  AND d.role_id = p.role_id
  AND d.permission_id = p.permission_id
  AND d.granted IS DISTINCT FROM p.granted;
```

### 7.3 UUID-default tables (10 of the 12 Behavioral)

For all other Behavioral tables, the `id` column is a UUID with implicit default. INSERT excludes `id` from the column list so the database generates a fresh UUID for each demo row:

```sql
INSERT INTO <T> (
    <all non-id non-tenant_id non-created_at non-updated_at columns>,
    tenant_id, created_at[, updated_at]
)
SELECT
    <same cols>,
    '8d8cfa7e...'::uuid AS tenant_id,
    now()[, now()]
FROM <T> p
WHERE p.tenant_id = '6ad0781b...'::uuid
  AND NOT EXISTS (
    SELECT 1 FROM <T> d
    WHERE d.tenant_id = '8d8cfa7e...'::uuid
      AND d.<business_key_cols> = p.<business_key_cols>
  );
```

UPDATE uses `md5(string_agg(...))`-style content comparison or column-by-column `IS DISTINCT FROM`. To minimize code complexity and maximize correctness, the Executor will use column-by-column `IS DISTINCT FROM` chained with OR — captures NULLs correctly without serialization concerns. The actual UPDATE SQL is built per-table from the column metadata.
