# M7 — Orders Feature Inventory

> **סטטוס:** Feature-Inventory (לא SPEC, לא Architecture Brief סופי).
> **מטרה:** לרכז את כל הפיצ'רים שדניאל דורש שיהיו במסך ההזמנה,
> כקלט ל-Architecture Brief של M7 שיכתב בשלב הבא.
> **מקור:** סקיצת Miro של דניאל (BackUp 29.6.25 Optic) + מסך Access הקיים +
> שיחת-התכנון מ-2026-05-07.
> **שפת-עבודה:** עברית. שמות-פיצ'רים באנגלית כשהם מהסקיצה המקורית.
> **בעלים:** דניאל (Product) + Main Strategic (Architecture).

---

## 1. עקרון-על

מסך ההזמנה לא חי לבד. הוא **טאב בתוך כרטיס הלקוח** (`Client's card`),
לצד 5 טאבים נוספים: Details, Vision Function, Glasses, Contact lenses, Update.
המעבר לקוח → מרשם → הזמנה הוא לחיצה בתוך אותה חלונית, לא ניווט בין מסכים.

זה החוק הארכיטקטוני הראשון של M7: **הזמנה היא ילד של לקוח, לא ישות עצמאית במסך**.

---

## 2. שורת-כותרת ההזמנה

- שם העובד שיצר את ההזמנה
- שם הלקוח + ID-לקוח (קליקבילי — מעבר חזרה לכרטיס)
- מספר-הזמנה רץ אוטומטית — לא ניתן לעריכה
- תאריך הזמנה — לא ניתן לעריכה לאחר יצירה
- 3 צ'קבוקסים לסוג ההזמנה: **Offer** (הצעת-מחיר) / **Repair** (תיקון) / **Reserve** (שמירה)
  - ברירת-מחדל: כולם לא מסומנים = הזמנת-מכירה רגילה

---

## 3. הזמנות-משניות — A / B / C / D / ... (פיצ'ר מרכזי)

### 3.1 הצורך
לקוח אחד יכול לקנות במכת-מכירה אחת מספר זוגות-משקפיים: רחוק, קריאה, שמש,
מולטיפוקל-נוסף, משקפיים לעבודה. ה-Access הציג רק 2 (A + B). דניאל דורש להסיר את התקרה.

### 3.2 הפתרון (מהסקיצה המקורית)
- כל הזמנה ראשית מכילה N הזמנות-משניות (A, B, C, D, ...).
- כל הזמנה-משנית היא יחידה עצמאית עם המסגרת שלה, העדשות שלה, הסטטוס שלה,
  התאריכים שלה והודעות-ה-WhatsApp שלה.
- במצב התחלתי גלויה רק A. אחרי שמסיימים את A — נפתח כפתור **+ הוסף הזמנה משנית**
  שמוסיף את B, ואחריו אפשר להוסיף C/D וכן הלאה.
- מספר ההזמנה-המשנית מסומן באות שמשורשרת לזיהוי-WhatsApp:
  פורמט הודעה = `{branch_num}-{order_num}-{sub_letter}`. דוגמה: `1-1122-A`.
- אין תקרה קשיחה במערכת. תקרה רכה (UX-בלבד) למניעת-טעות: אם נפתחו 6+
  הזמנות-משניות, מציגים אישור "האם זה באמת זוג נוסף?".

### 3.3 פתרונות-UI אפשריים (להחליט ב-Architecture Brief)
- **Accordion אנכי** — כל הזמנת-משנה היא מקטע מתקפל. רק אחת פתוחה בכל רגע.
- **טאבים-משניים אופקיים** — A | B | C | D + כפתור `+`. מתאים אם מספר ההזמנות-המשניות נשאר קטן (≤6).
- **רשימה-עם-פאנל-עריכה** — צד-ימין רשימת-A/B/C, צד-שמאל פרטי-הנבחרת. סקיילבילי באמת.
- **עדיפות מומלצת:** Accordion עד 4, אוטומטית-עובר ל-list-with-panel מ-5+.

## 4. הזמנת-משנית — שדות-ליבה (חוזר על עצמו לכל A/B/C/...)

### 4.1 כותרת ההזמנה-המשנית
- אות-זיהוי (A/B/...) + כפתור-WhatsApp צבוע ייחודית להזמנה-משנית
- צ'קבוקס **Task** — פתיחת-משימה למנהל (למשל: לבדוק מחיר XYZ)
- שדה **Note** — הערה חופשית
- כפתור **Call Back** + תאריך + שעה + צ'קבוקס Called (סומן כהוחזר-טלפון)
- שדה **Per. Date** — תאריך-המרשם שעליו מבוססת ההזמנה (חובה אם יש עדשות)
- כפתור **Add. info** — פותח חלונית-הזמנה-מלאה (כל-השדות-המורחבים)

### 4.2 בורר סוג-מסגרת (3 צ'קבוקסים בלעדיים-זה-לזה)
- **Contact Lenses** — הזמנת-עדשות-מגע (ללא מסגרת)
- **Optical** — מסגרת אופטית רגילה
- **Sun** — מסגרת-שמש

### 4.3 בלוק עדשות (כשהסוג Optical/Sun)
- שדה **Right Lens** — סריקת-ברקוד או בחירה ידנית
- שדה **Left Lens** — אותו דבר
- שדה **Frame** — סריקת-ברקוד או בחירה ידנית
- שדה **Height** (גובה האישון בעדשה) — חובה כשעדשות מוזמנות
- כפתור-Info צף שנפתח אוטומטית בסריקת-ברקוד ומציג: Brand / Lens-Type / Index /
  Diam / Coating / CYL / SPH / Sell-Price / Discount

### 4.4 בלוק עדשות-מגע (כשהסוג Contact Lenses)
- שדה **Category** (סוג: יומיות / חודשיות / שלושה-חודשים / שנתיות)
- שדה **Inv.Shelf** (מקור: מלאי / הזמנה מהספק)
- שדה **Right Lens** + שדה **Left Lens**
- כפתור-Info צף שמציג: Supplier / Brand / Model / Size / Color / Sell-Price / Discount

### 4.5 בלוק מחיר
- שדה **Pre-Discount** (מחיר לפני הנחה)
- שדה **%** (אחוז הנחה)
- שדה **Total** (מחיר סופי אחרי הנחה — מחושב אוטומטית)

### 4.6 בלוק סטטוסים ותאריכים
- צ'קבוקס **Informed** — הלקוח עודכן (סומן אוטומטית כשנשלחה הודעת WhatsApp)
- שדה **Order Ready** + תאריך
- שדה **Delivered** + תאריך + כפתור-הדפסת-טופס-מסירה
- שדה **Sent for Framing** + תאריך + כפתור-הדפסת-תווית
- שדה **Type** (Distance / Reading / Multifocal / Office)
- שדה **Location** (Shop / Lab / Lens-only)
- שדה **Lenses Ordered** + תאריך + כפתור-הדפסת-תווית

### 4.7 כפתור Order Form
- פתיחת חלונית-הזמנה-מורחבת לעריכת כל השדות בבת-אחת.

### 4.8 נעילת-טופס (Lock-Next-Item)
- B/C/D נעולים ולא ניתנים-לעריכה כל עוד הקודם פתוח.
- אחרי שמירה של A, מתאפשר ללחוץ + להוסיף B.

## 5. סינונים-וכפיות-שדה לפי המרשם

- העדשות שמוצגות בבחירה מסוננות לפי המרשם הפעיל. דוגמה: מרשם SPH -2.00 / -3.00 →
  רק עדשות שמכסות את הטווח.
- אדמין יכול להגדיר **שדות-חובה דינמיים לפי בחירה**:
  למשל "אם נבחר Multifocal-lenses → corridor-length הופך לחובה".
- אדמין יכול להגדיר **שדות-חובה דינמיים לפי סוג-מסגרת**:
  Frame Type / Width / Height / Diagonal / Bridge / Segments-Height / Corridor-Length —
  כל אחד יכול להיות חובה/רשות לפי הקונפיגורציה של העסק.

## 6. אביזרים והנחות (איזור-תחתון)

- בלוק **Accessories** — תיאור + מחיר. ברירת-מחדל מהקטלוג (Lens Liquid וכו'),
  עם אפשרות להוסיף שורות נוספות.
- בלוק **Additional** — תיאור-חופשי + מחיר. שורות שאדמין מאפשר.
- שדה **Coupon** — קוד-קופון. הקופון יכול להיות מוגבל (sunglasses-only, lenses-only,
  brand-only). הולך לפי הגדרת-הקופון במודול-הקופונים.
- שדה **Sale** — מבצע/הנחה כללית.
- שדה **Credit** — זיכוי שניצמד לחשבון הלקוח.
- שדה **Tax** — מע״מ (אוטומטי לפי tenant config).
- שדה **Discount** + **%** — הנחה ידנית.
- שדה **Total Bill** — סה״כ-לתשלום.
- שדה **Missing** — חסר-לתשלום.
- שדה **Payed** — שולם-עד-עכשיו.
- כפתור **Payment** — פותח חלון-תשלומים מלא:
  - שיטת-תשלום (CC / Cash / Bit / העברה)
  - תאריך-תשלום
  - מספר-חשבון / מספר-אשראי
  - סניף + בנק
  - תיאור
  - מספר-תשלומים
  - סכום
  - היסטוריית-תשלומים מלאה (כל התשלומים שבוצעו)
  - מסונכרן-עם-קופה (מודול הנהלת-חשבונות)
  - מחיקת-תשלום מותרת רק למנהל ורק אם לא עבר-לקופה

## 9. WhatsApp + רב-לשוני

### 9.1 בורר-שפה
- HE / RU / EN — נטען אוטומטית לפי שפת-הלקוח שהוגדרה בכרטיס.
- ניתן לשינוי-ידני להזמנה ספציפית ("הלקוח מעדיף עברית להודעה הזאת").
- הקונפיגורציה גמישה — אדמין יכול להוסיף שפה רביעית בעתיד (ערבית, צרפתית).

### 9.2 4 כפתורי-תבניות מהירות
- **Purchase** — תודה על הקנייה
- **Review** — בקשת ביקורת/חוות-דעת
- **Something** — תזכורת כללית (free template)
- **All Ready** — הכל מוכן, ניתן לבוא לאסוף

### 9.3 תיבת-טקסט-חופשית
- ההודעה נטענת אוטומטית לפי הכפתור שנלחץ.
- ניתן לעריכה לפני שליחה.
- אחרי לחיצה על Send — התיבה מתנקה.
- שליחה מסמנת אוטומטית **Informed** = TRUE.

### 9.4 הודעות-מולטיפוקל אוטומטיות
- צ'קבוקס **1st Multifocal Message** — הודעת-הסבר ראשונה אחרי קנייה ראשונה של מולטיפוקל.
- צ'קבוקס **2nd Multifocal Message** — מעקב אחרי שבוע.
- שתיהן נשלחות אוטומטית בשפת הלקוח, ניתנות-לשינוי-ידני.

### 9.5 לוגיקת השליחה הקבוצתית
- בהזמנה עם A+B+C+... יש בחירה: לשלוח הודעת-"All Ready" כשכל-ההזמנות-המשניות
  מוכנות (ברירת-מחדל), או לשלוח הודעה נפרדת על כל הזמנת-משנה כשהיא מוכנה
  (לחיצה כפולה על האות + סימון).

## 14. כללי-עסק (Business Rules)

- **חובת-מרשם-לעדשות:** אם ההזמנה כוללת עדשות (משקפיים או מגע), חייב לבחור
  מרשם פעיל. בלי מרשם — לא ניתן לשמור.
- **תאריך-מרשם חובה:** Per. Date חייב להיות מלא לכל הזמנת-עדשות.
- **מספר-הזמנה רץ:** לא ניתן לעריכה אחרי יצירה. שימוש ב-RPC עם FOR UPDATE לפי Iron Rule 11.
- **soft-delete בלבד:** מחיקת-הזמנה לא מוחקת מה-DB. דורש PIN לפי Iron Rule 3.
- **כל שינוי-מחיר נרשם ל-writeLog** לפי Iron Rule 2.
- **סריקת-ברקוד פותחת אוטומטית חלונית-Info** למסגרות ולעדשות.

## 15. תצורות-לפי-Tenant (SaaS)

הכל-מ-DB, שום-דבר-קשיח-בקוד (Iron Rule 9 + Iron Rule 20):
- אילו 3 הסוגים שמופיעים בשורת-הכותרת (Offer/Repair/Reserve או אחרים)
- אילו שדות-מסגרת הופכים לחובה לפי בחירת-מסגרת (Frame Type / Width / Height / Bridge / ...)
- אילו 4 תבניות-WhatsApp מופיעות בכפתורי-המהירים
- אילו שפות זמינות (HE/RU/EN + הרחבה)
- אילו טפסי-הדפסה זמינים (Repair/Reserve/Task/Offer/Order+Per. + הרחבה)
- אילו אביזרים מופיעים בברירת-מחדל ב-Accessories
- מי יכול למחוק תשלום (תפקיד / PIN-נדרש)
- מתי הקופון תקף (sunglasses-only / lenses-only / brand-only / general)
- מה גובה המע״מ (אחוז) ומאיזה תאריך

## 16. אינטגרציות עם מודולים אחרים

- **M11 — Accounting (עתידי):** Payment מסונכרן עם קופה.
- **M4 — CRM:** Note + Manager-Escalation יוצרים אוטומטית רשומות במודול-CRM.
- **M12 — Messaging:** WhatsApp עובר דרך Edge Function "send-message" (לפי Messaging Architecture v2).

## 18. פיצ'רים שצריכים החלטה לפני Architecture Brief

הרשימה הזאת היא רשימת-פתוחים שיגיעו ל-Foreman SPEC כשאלות-תכנון:

1. **UI להזמנות-משניות מרובות:** Accordion / Sub-Tabs / Master-Detail? (סעיף 3.3)
2. **תקרה-רכה למספר ההזמנות-המשניות:** האם להציג אזהרה ב-6+? ב-8+?
3. **אורך-חיים של Offer:** הצעת-מחיר פגה אוטומטית אחרי X ימים? קונפיגורבילי?
4. **שכפול-מרשם בין-הזמנות:** A ו-B חייבים אותו מרשם או יכולים להיות שונים?
5. **פעולה-המונית:** "כל ההזמנות-המשניות מוכנות" — האם זה כפתור-יחיד או נגזר מסטטוסים?
6. **חיווי-הקדימויות בהזמנה:** האם לסמן ויזואלית הזמנת-משנה שמחכה לספק יותר מ-X ימים?
7. **תמיכה ב-Tablets ו-Mobile:** המסך הזה גם בטלפון של מנהל? אם כן, איזה sub-set מוצג?

## 19. תוספות אחרי סקירה-שנייה של התמונה (2026-05-07)

הפריטים האלה עברו מתחת לרדאר בסבב הראשון. נוספים כאן:

### 19.1 כפתור-מחיקה (סל-אשפה) ליד כל שורת-עדשה
בתמונה הקרובה רואים כפתור 🗑 ליד כל שורת Right Lens / Left Lens / Frame.

### 19.2 כפתור-תפריט (3-נקודות / hamburger) ליד כל שורת-עדשה
ליד הכפתור המחיקה רואים אייקון נוסף — תפריט פעולות מהירות לעדשה:
- החלפה בעדשה אחרת מהמלאי
- שינוי-מחיר ידני (עם PIN-מנהל)
- העברה להזמנת-משנה אחרת (B → C)
- הצמדת note לעדשה הספציפית

### 19.3 כפתור-Info לכל סריקת-ברקוד עם 2 חלוניות נפרדות
בתמונה רואים שתי חלוניות-Info שונות בראש המסך:
- **חלונית-עדשות:** Brand / Lens-Type / Index / Diam / Coating / CYL / SPH / Sell-Price / Discount
- **חלונית-מסגרות:** Supplier / Brand / Model / Size / Color / Sell-Price / Discount

הן נפתחות אוטומטית בסריקת-ברקוד ונסגרות בלחיצה על Close או Enter.
זה מנגנון verify-before-add — העובד רואה מה הוא מוסיף לפני ששורת-העדשה נכנסת להזמנה.

### 19.4 שורת-Add-Note נפרדת בכל הזמנה-משנית
שמתי לב שיש Note ברמת-ההזמנה-המשנית (4.1) וגם Note כלליים-להזמנה (סעיף 7).
**זה שני דברים שונים:**
- Note ברמת-משנית: הקשר של אותה משקפיים ספציפיים ("עדשות הגיעו פגומות")
- Note ברמת-הזמנה: הקשר עסקי כולל ("לקוח רצה לקנות נוזל לעדשות לארוחה אצל חברו")

המסמך ב-§4.1 ו-§7 צריך לשמור על האבחנה הזאת.

### 19.5 כפתור-הדפסה בודד ליד כל תאריך-סטטוס
לכל תאריך בבלוק-הסטטוסים (§4.6) יש 🖨 משלו:
- Order Ready 🖨 → תווית-מוכן-לאיסוף
- Delivered 🖨 → טופס-מסירה (חתימת לקוח)
- Sent for Framing 🖨 → תווית-לבית-מלאכה
- Lenses Ordered 🖨 → תווית-להזמנה-לספק

זה לא רק "Order+Per." הכללי בתחתית. כל סטטוס מדפיס משהו אחר, ובהקשר אחר של ה-flow.

### 19.6 צ'קבוקס Informed שמסתנכרן עם WhatsApp
ה-Informed נדלק אוטומטית כש-WhatsApp נשלח. אבל גם אפשר לסמן ידנית
("דיברתי איתו בטלפון, הוא יודע"). הסטטוס הזה משפיע על דוחות-CRM של leads-שלא-עודכנו.

### 19.7 כפתור Reset לרשימת-תשלומים
בחלון Payment בתמונה הרחבה רואים כפתור Delete + Reset.
- Delete: מוחק תשלום-בודד (PIN-מנהל)
- Reset: איפוס מלא של כל תשלומי-ההזמנה (PIN-מנהל-ראשי + log חמור)

זה פיצ'ר רגיש — אסור שיהיה זמין לעובדי-קופה רגילים.

## 21. תוספות מטקסט-האפיון של דניאל (2026-05-07)

הסעיף הזה משלים מה שהיה במסך-Access אבל לא תועד בסקירת-התמונה. מקור:
טקסט-אפיון של דניאל ("Orders Screen – Simplified Explanation").

### 21.1 Order Type — הרחבה של הצ'קבוקסים
ב-§2 דיברנו על Offer/Repair/Reserve. הסיווג הנכון רחב יותר:
- **Regular** — ברירת-מחדל. מוריד מהמלאי.
- **Quote** — הצעת-מחיר. לא משפיע על מלאי. ניתנת להמרה ל-Regular בעתיד עם שמירת ההיסטוריה.
- **Repair** — נוצר לרוב מלחיצת **Duplicate** על הזמנה ישנה. אין הורדה ממלאי.
  המשתמש בוחר מה לתקן (חלק-במסגרת / עדשות / שניהם). מקבל מספר-הזמנה חדש.
- **Frame Reservation** — לקוח בחר מסגרת אבל לא עשה בדיקת-ראייה. **המסגרת יורדת
  ממלאי מיד** (לא ממתינה להזמנה הסופית). המערכת חייבת להציג רשימה של כל
  ההזמנות-בשמירה עם התראה כשמשהו "שומר יותר מדי זמן". ניתנת להמרה ל-Regular
  באמצעות כפתור **Convert to Order** — הסטטוס משתנה ל-Ordered, ההיסטוריה
  של ה-Reservation נשארת מקושרת להזמנה החדשה לדוחות.
- **Task** — משימה ללא מלאי. שלושה תרחישים: מעקב על הזמנה ישנה, לקוח-חדש
  שמבקש בדיקת-מחיר, או escalation למנהל. כל Task יוצר אוטומטית התראה ביומן.

### 21.2 Category לכל הזמנה-משנית (חובה לדוחות)
חסר ב-v0.2: הגדרת **Category** מפורשת לכל הזמנה-משנית. חייב להיות אחד מ:
- Sunglasses
- Eyeglasses
- Contact Lenses

תמיכה ב-**Sub-Categories** מתחת לכל קטגוריה. דוגמה: תחת Eyeglasses אפשר Progressive,
Office, Stock-lenses וכו'. הקטגוריות והתת-קטגוריות מוגדרות ב-tenant config (Iron Rule 19),
לא קשיחות בקוד. דוחות חייבים לתמוך באגרגציה לפי קטגוריה ותת-קטגוריה גם יחד —
זה בסיס לחישוב profit-margin שמשתנה דרמטית בין סוגי-מוצרים.

### 21.3 פריט ב-4 צורות-נפרדות (לא רק עדשות+מסגרת)
v0.2 הציג Frame + Lenses + Contact-Lenses + Accessories. הסיווג הנכון:
- **Frame** — יורד תמיד ממלאי. כמות-ברירת-מחדל 1, ניתנת לעריכה.
- **Lenses** — יש סוגים שיורדים ממלאי (in-stock) ויש שלא (special-order). מסומן ב-catalog.
- **Accessories** — יורד-ממלאי-או-לא **לפי הגדרת-הפריט בקטלוג** (לא לפי בחירה ידנית).
- **Free-Text Line Item** — תיאור-חופשי + מחיר. **דורש אישור-מנהל (PIN)** כדי
  להוסיף. נכלל בסכום-הסופי אבל **לא משפיע על מלאי**. שימוש: שירות / מוצר שעדיין
  לא בקטלוג / התאמה אישית.

### 21.4 מודל הנחות מורחב (חמישה רובדים)
v0.2 נתן Discount + Coupon + Sale. הטקסט שלך מפרק לחמישה רובדים שונים שעובדים יחד:
- **Line-Level Discounts** — הנחה על-עדשה / על-מסגרת / על-שניהם. אפשר להגביל
  לקטגוריה ספציפית (רק על Multifocal של מותג XXX).
- **Group Discounts** — הנחות-קבוצה מוגדרות-מראש (חברי קופ״ח, חברי-מועדון).
  המשתמש בוחר מ-dropdown, ההנחה מחושבת אוטומטית לפי כללי-הקבוצה.
- **Coupon Codes** — קוד-קופון עם כללים מוגדרים-מראש (סכום-קבוע / אחוז / קטגוריה).
- **Customer Balance / Credit** — יתרת-זכות מהזמנות קודמות (החזרים, תשלומים-עודפים)
  משמשת אמצעי-תשלום בהזמנה הנוכחית.
- **Discount Stacking Rules** — **ברירת-מחדל: הנחות לא מצטברות**, כל הנחה חוסמת
  את האחרות. צבירה אפשרית **רק אם מותר במפורש** בהגדרת-הקופון או ההנחה.

### 21.5 VAT — קונפיגורבילי (כולל "כולל-מע״מ" מול "פלוס-מע״מ")

v0.2 נתן 4 תאריכים. הטקסט שלך מוסיף:

- מנהל יכול לראות timestamp מלא לכל מעבר-סטטוס לצורכי audit (פולשן, סכסוכים).
- שינוי-ידני של תאריך נרשם ל-log עם המשתמש שביצע.

v0.2 הזכיר Location כשדה פשוט. הדינמיקה הנכונה:

  "Lab", "התקבל מהבית-המלאכה" → "Shop").
- בכל רגע אפשר **override ידני** (חשוב במיוחד לתיקונים).
- 3 מיקומים-טיפוסיים לתיקון:
  - המסגרת **אצל הלקוח** (הלקוח לוקח אותה הביתה ומחכה לחלק-חילוף)
  - המסגרת **בחנות** (מחכה למשהו)
  - המסגרת **בבית-מלאכה חיצוני**

v0.2 נתן Task כצ'קבוקס. בפועל:

- **כללי-ללקוח-קיים** (להתקשר בעוד שבוע).
- **כללי-ל-Lead** (לקוח-חדש שעדיין לא קנה — בקשת-מחיר וכו').
- כל Task: מופיע ביומן, צבוע ייחודית עד-לסיום, חובת תאריך-יעד (default קונפיגורבילי).

### 21.9 ארכיטקטורת-הודעות עם 2 מספרי-טלפון נפרדים
v0.2 הזכיר WhatsApp. הטקסט שלך קובע ארכיטקטורת-הודעות מורכבת יותר:
- **מספר-מאומת ב-Meta/WhatsApp Business** — לכל ההודעות-האוטומטיות והתבניות-המאושרות.
- **מספר-נפרד (Green API)** — להודעות-טקסט-חופשיות-ידניות.
- **מספר-נוסף "ניהול/שירות"** — אופציונלי, למקרים מיוחדים (לקוח-VIP, תלונה,
  הודעה ממנהל מבלי לחשוף את מספר-הסניף). זמין **רק למנהלים**.
- מסתדר עם Messaging-Architecture-v2 הקיים: Make=send-only-pipe, Edge-Function=logic.

### 21.10 Templates ב-Meta — תהליך-אישור
v0.2 הזכיר תבניות. הכלל החשוב:
- **תבנית-חדשה ניתן ליצור רק אחרי אישור-Meta** (Admin בלבד, לא משתמש-רגיל).
- תמיכה ב-3 שפות חובה: עברית, רוסית, אנגלית.
- שליחה אוטומטית בשפת-הלקוח. אפשרות-override-ידני לפני שליחה.

### 21.11 Trigger Logic מפורש (If–Then engine)
v0.2 הזכיר manager-escalation. הטקסט מוסיף שכבה רחבה יותר:
- **engine של חוקים If–Then** מובנה לתוך המודול. דוגמה:
  "אם הודעת-Order-Ready נשלחה → עדכן Order-Ready-Date אוטומטית".
- **חוקים נוספים יוגדרו בעתיד** ע״י Admin בלי קוד.
- ברירת-מחדל: שדה-תאריך לא ניתן לעדכון-ידני בלי שליחת-הודעה. Admin יכול להחריג.

### 21.12 Cancel Order — flow מלא (לא רק כפתור)
v0.2 הציג Cancel-Order ככפתור. ה-flow הנכון:
- דורש **אישור-מנהל**.
- pop-up שואל איך מטפלים בכסף שכבר שולם:
  - **Full refund** (החזר מלא)
  - **Partial refund** (אחוז או סכום ידני)
  - **Store credit** (יתרת-זכות לחשבון הלקוח)
- נרשם **המשתמש שביקש את הביטול** (חיוני ל-audit).
- ההזמנה נשארת ב-DB עם דגל cancelled + audit-trail מלא. **לא נמחקת**.

### 21.13 Delete Order — מותר רק להזמנה האחרונה
v0.2 הציג Delete-Order. החוק הקריטי שחסר:
- **מחיקה אפשרית רק להזמנה האחרונה של הלקוח** (אחרת נשבר רצף-מספרים והפניות).
- דורש **אישור-מנהל** (PIN-double לפי Iron Rule 3).
- כל הפריטים **מוחזרים למלאי** אוטומטית.
- ההזמנה מסומנת **Deleted (תווית-אדומה)**, נשארת בהיסטוריה ב-read-only.

### 21.14 מקדמה-מינימלית (Minimum Deposit %)
פיצ'ר חדש לחלוטין שלא היה ב-v0.2:
- Admin מגדיר **אחוז-מקדמה-מינימלי** ברמת-tenant (דוגמה: 50%).
- חישוב: הזמנה ב-1,000 ₪ עם min-deposit 50% → הלקוח חייב לשלם לפחות 500 ₪
  כדי **לאשר את ההזמנה במערכת**.
- היתרה (500 ₪) נדרשת בעת איסוף-ההזמנה.
- אם הלקוח שילם פחות מהמינימום → ההזמנה לא נשמרת או נשמרת כ-pending.

### 21.15 כללים-עסקיים נוספים שצוינו בטקסט
- כל הזמנה עם **עדשות-עם-מספרים** או **עדשות-מגע** מחייבת **Prescription Date**.
- ניתן לבחור מרשם-קיים-שמור ל-auto-fill בעת יצירת-הזמנה-חדשה.
- Order-Number-Field רץ אוטומטית, לא ניתן לעריכה.
- Free-Text-Line-Item ופעולות-רגישות (הנחות, ביטולים, מחיקות) **כולן דורשות
  PIN-מנהל ונרשמות ל-log**.

## 23. שאלות-תכנון נוספות שעלו (משלימות את §18)
